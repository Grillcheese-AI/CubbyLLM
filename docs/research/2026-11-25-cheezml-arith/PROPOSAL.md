# CheezML terms for an arithmetic certificate (order 0085): a proposal for Nick

Status: proposed by Claude Code (Code A), 2026-11-25, on Nick's choice ("draft new terms"). The vocabulary is Nick's;
nothing here is in `vendor/cheezml`. The executable form is `validation/cheez_proposal.py` (the pin's shapes changed
in memory), and `tests/records/test_cheez_arith.py` checks it.

## Why v0.2 cannot say it
An arithmetic answer (order 0078) is a chain of VM runs over numbers the host read from the question. Measured with
the pin's shapes (`validation/cheez_shapes.py`, which accepts the pin's 8 examples and rejects its 15 broken ones),
v0.2 refuses a certificate for it on three counts:
1. **CertifyingRunShape:** the certifying run must have used a `cheez:FactVersion` ("one version of a stored
   statement") whose source records its revision. The question's numbers are not stored statements.
2. **ProgramRunShape:** a run that read a fact version names a store snapshot and an as-of time. There is no store.
3. **CertificateShape / CheckRunShape:** a certificate needs at least one satisfied check, of a kind in
   `cheez:CheckKinds`. None of the 20 kinds is the slot check, the vote or the answer-kind rules.

A refusal fits v0.2 as it is (`cubby:NoPlan` or `cubby:NotCertified`), and the writer writes those today.

## What is proposed
**New concepts (5 check kinds, 1 threshold parameter, 2 artifact kinds):**

| term | scheme | definition |
|---|---|---|
| `cubby:SlotCheck` | `cheez:CheckKinds` | Every number and name in the step programs is a slot the host placed from the question: no copied literal, no unknown slot (H-E15). |
| `cubby:VoteCheck` | `cheez:CheckKinds` | At least m of the first k tries reached the same VM value, and no other value tied it. Observed value: the votes; threshold: m. |
| `cubby:NonNegativeCheck` | `cheez:CheckKinds` | The answer is not negative (0078 addendum, rule a). |
| `cubby:WholeCountCheck` | `cheez:CheckKinds` | A "how many" of a thing that is not a measure is a whole number (rule b; the measures are a closed list). |
| `cubby:MoneyDecimalsCheck` | `cheez:CheckKinds` | A money "how much" has at most 2 decimals (rule c). |
| `cubby:SpeakVotes` | threshold parameters (ThresholdShape's list) | m: the fewest tries that must reach one VM value for the answer to be said. It is calibrated on dev, like every threshold. |
| `cheez:AdapterWeights` | `cheez:ArtifactKinds` | An adapter's weights, by hash (the emitter's LoRA). |
| `cheez:Settings` | `cheez:ArtifactKinds` | A read's frozen settings (k, m, temperature, top-k, rules), by hash. |

**One namespace allowed, nothing minted:** the W3C Web Annotation vocabulary (`http://www.w3.org/ns/oa#`), for where
a number was read: `oa:hasSelector` on a `cubby:DocumentRegion`, an `oa:TextPositionSelector` with `oa:start` and
`oa:end` (character offsets into the question). Add the namespace to `tools/validate.py`'s ALLOWED list and to the
context (`oa`; `oa:start` and `oa:end` as `xsd:nonNegativeInteger`).

**One shape changed, CertifyingRunShape:** the run, or a run it was informed by (`prov:wasInformedBy`, any number
of steps), used at least one statement version whose source records its revision, **or** at least one field read
from a region of a hashed question (a `cubby:FieldSuggestion` whose region `schema:isPartOf` a `cheez:Artifact`).
The certificate's message changes to say so. Nothing else is loosened: one program per run, the run returned,
every check satisfied by the chosen program, the answer generated by the certifying run. A run that read no fact
version already needs no store snapshot.

## How an arithmetic certificate uses them (`cubbyllm/records/cheez_arith.py`)
- **The question:** a `cheez:Artifact` by its SHA-256.
- **Each `$N`:** a `cubby:DocumentRegion` (the text as read, the reader, `schema:isPartOf` the question, its
  selector), and a `cubby:FieldSuggestion` (the value the host filled in, `cubby:region`, the slot id as
  `schema:identifier`).
- **Each `$K`:** a `prov:Entity` (its value, the fact as `schema:name`) `prov:wasDerivedFrom` the arithmetic
  world's closed list (a `cheez:Rule` by hash).
- **Each step:** a `cube:Program` (the SHA-256 of the whole filled program the VM ran; `prov:wasDerivedFrom` the
  adapter) and a `cube:ProgramRun` that used it and the slots it names, `prov:wasInformedBy` the runs whose `$S` it
  used. Its value is a `prov:Entity` `prov:wasGeneratedBy` that run. The certifying run is the one that made the
  stop's `$S`.
- **The VM build:** `schema:version` (the commit) on the `cube:VM`.
- **The checks, all on the certificate, each satisfied by the chosen program:** the slot check (over every step's
  program), the vote (votes observed, m as a `cheez:Threshold` of `cubby:SpeakVotes`, generated by a
  `cheez:Calibration` whose data is the dev rows m was chosen on and whose encoder is the adapter), and one check per
  answer-kind rule that applies.

## What stays outside the record, in the trace beside it (order 0085's records file)
- every try's final value (the vote's inputs; the record has only the count that agreed);
- the rules that did not apply to the question (a check that never ran has no record);
- the step programs' text (an artifact is referenced by hash, never embedded); the trace keeps each step as the VM
  got it, which the replay re-fills and re-hashes.

## Checked
- With the proposal, the pin's 8 examples still conform and its 15 negative ones still fail.
- An arithmetic certificate fails at the pin (the three counts above) and conforms with the proposal. One whose runs
  used no number of the question still fails, with the new message.
- 5 dev questions run through the real VM with their gold steps: 5 certificates, 0 conform at the pin, 5 under the
  proposal, every replay `same`.
