# Growing base450m to 1-1.5B without training from scratch (2026-09-25)

Status: RESEARCH. Nothing here has been run. As in `2026-09-23-training-acceleration.md`, each number is **measured** (log linked), **sourced** (arXiv id), or **computed** (marked). This note refines Route A's phase 2 ("grow on an H100") for a 1-1.5B target.

## TL;DR

- The base is smaller and less trained than its name suggests: **576M parameters, of which 262M are the untied embedding and head, and only 314M are the trunk**. It saw **2.77B tokens**, about 9 per trunk parameter, and ~16% of the 17.7B-token cache. That is the regime where growth pays most, because the small model has not saturated.
- Every layer type in the base can be grown **function-preservingly**: the grown model computes exactly the base's outputs before its first step. So day 0 of the bigger model is today's model, and every gate (E6-E9) starts from today's numbers.
- Five shapes land in 1-1.5B. The cheapest to reach, per the published evidence and our throughput, are **depth ×2 + FFN ×2 (1.29B)** and **width ×2 (the planned d2048, 1.26B trunk / 1.78B total)**.
- **The control that matters is continuing the 450M itself.** It is undertrained, so more tokens alone will lower its loss. Growth is worth it only if a grown arm beats that control at equal compute.
- Plan: a local step 0 (exactness check, no GPU cost), a ~4 A100-hour pilot with 4 arms, then ~20 H100-hours (~$40-60) for the winner, then the talk adapter retrained (~30 min) and the gates re-run. About 2-3 days of wall-clock.

How to read it:
- **A** is Route A's planned "2B shape". It fits 1-1.5B only if the count excludes embeddings. It doubles the embedding and head (262M → 524M of parameters that do not think), but keeps 32 layers, so decode latency on grilly2 grows least.
- **D** keeps the embedding at 262M, so almost all the new parameters go to the trunk. It doubles the layers, so decode latency roughly doubles (per-token cost on grilly2 is layer-launch-bound at batch 1).
- **E** is the cheapest per token but adds no compute per token. The 23 Sep panel kept MoE for cycle two (grouped-GEMM kernels, token tax), and it adds parametric memory, which the design keeps outside the weights. Not proposed for this step.
- **C** needs masked growth, since 1.5× is not an integer clone. That is more engineering for a smaller model than A or D.

## 3. Why every layer can start exact (derivation; step 0 checks it)

No published work grows a MinGRU-style hybrid. The research agent found none, and RWKV-X (2504.21463) and the RWKV-7 upgrade (2503.14456) are the only recurrent cases. The argument below is ours.

**Width ×2 (HyperCloning).** Each weight W becomes the 2×2 block [[W/2, W/2], [W/2, W/2]], and each hidden state becomes [h, h].
- **Recurrent mixer.** Decay, gate and value are per-channel linears with biases, so the bias becomes [b, b]. The recurrence is elementwise, so the state becomes [s, s].
- **RMSNorm.** The RMS of [h, h] is the RMS of h, so the gains are simply repeated.
- **Attention.** The 4 heads × 256 become 8 heads × 256, with each head duplicated. Head size is unchanged, so the 1/√256 scale and RoPE are unchanged. o_proj takes the block form in head order.
- **Embedding and head.** The embedding becomes [E, E]. The untied head becomes [H/2, H/2], so the logits are unchanged.
- **Generated adapter and router.** The adapter's A/B bases and the router's input projection are cloned along the 1024 axis the same way.

**Depth ×2.** As built, each block of 3 layers (attention, recurrent, recurrent) is followed by its copy. `HybridBackbone` decides a layer's kind from its index (attention where i % 3 = 0), so copying block by block keeps every layer's kind with no model change. The 2 tail layers of 32 are copied by kind. G_stack's whole-stack copy would need an explicit layer pattern in the model and in grilly2; that is a small change, left until the pilot asks for it. The new copy's contribution to the residual stream starts at zero, so the model is exact:
- **FFN:** down_proj set to 0.
- **Attention:** o_proj set to 0.
- **Recurrent mixer:** it has no output projection. As built, value's weight and bias are set to 0, which keeps tanh(value) and the state at 0. The copy's gate and decay are kept. A ramp from 0 to 1 on the output (MSG's mask) would keep the value weights too; it is not built.
- **Generated adapter:** the new layers' embeddings copy their source layers'.
- G_stack itself copies without zeroing (not exact) and found that fine. The zero-exit version costs nothing to try and keeps the day-0 guarantee.

**FFN ×2.** Each FFN gains new units: gate/up rows copied from existing units, plus small noise to break the symmetry, and down_proj columns set to 0. The model is exact.

## 4. The recipe for the grown run (sourced)

- **Re-warm, then decay.** Both kept checkpoints are annealed. Re-warm to about the base's peak LR (6e-4) over ~300 steps, hold, and end with a 20% WSD decay.
  - Re-warming to the pretraining peak did best for upcycling and did not cause forgetting (2410.07524).
  - Re-warm, re-decay and replay matched full retraining at 405M and 10B (2403.08763).
- **Train every parameter.** Freezing the old layers is for adding a domain without forgetting (Llama Pro, 2401.02415), not for adding capacity.
- **Data**
  - Mostly the unseen ~84% of the cache. The base trained on a 35% subset of the pinned 17.74B-token cache (`make_base_cache.py`: evenly spaced 1M-token blocks of each shard, plus each shard's held-out tail), drawing up to ~1.5 epochs of some shards. The long run should get a fresh subset made of the other blocks. The 1-hour pilot can reuse the subset with a new seed; every arm sees the same data, so the comparison stays fair.
  - Replay the base's mix at ~10-20% against early forgetting, which HyperCloning reports right after expansion.
  - The best slice, plus the instruction, dialogue and program data, goes in the decay, as in the base run.
- **Growth factor 2.** Factors of 2-4 were best in G_stack's IsoFLOP sweeps, and 2× was the most reliable for width (2605.13405). Gains fade once a width-grown model's budget passes ~20 tokens per parameter (2605.13405). Ours stays at ~2-5 (computed from §2), which is inside the regime where growth helps.
- **Distillation from a larger teacher: not in this step.** It pays in short continuations (2502.08606; 2410.16215: +1.6% for a 1.9B student on 100B tokens). But the teacher's forward pass over every token adds its own compute to each step. The settled plan keeps ULD-KD after pretraining.

## 5. Step 0 and the pilot (pre-registered; the numbers are the owner's to move)

**Step 0: local, no GPU rental**
- Write `cubbyllm/model/grow.py` with three operations: width clone, depth stack (zero exit or ramp), and FFN widen. Pin them with tests.
- Grow the base with each operation. Its validation mix loss on the base's held sequences must equal 2.3615 within bf16 noise; otherwise the operation is wrong.
- For the not-exact G_stack copy, record the jump.
- Load each grown export through grilly2 `models/cubby.py`. The first-token logits must match torch.

**Pilot: ~1 A100-hour per arm on Colab, 4 arms**
- Every arm uses the same data order (unseen cache), the same re-warm, and 131k tok/step.
- Arms:
  0. The 450M continued (the control).
  1. A, width ×2.
  2. D, depth ×2 + FFN ×2, zero-exit.
  3. D with G_stack's plain copy (not exact).
- Read validation mix loss plus EN, FR and code per domain, at equal wall-clock and at equal FLOPs, with the loss slope fitted over the last half of each arm.
- **Pick:** the arm whose fitted loss is lowest at 20 H100-hours.
- **Kill growth, for now:** no grown arm is ≥ 0.03 nats below the control at equal wall-clock by the end of the pilot, and no grown arm's slope reaches that by 20 H100-hours. The 450M then keeps training on the unseen cache instead, which is cheaper and faster to serve.

**Then**
- The winner runs ~20 H100-hours (~$40-60), about 3-4B tokens.
- talk_v2.1's mix retrains the talk adapter on it (~30 min; the adapters are shape-specific).
- Gates E6, E7, E8 and E9 are re-run unchanged. The grown model counts only if every gate is at least talk_v2.1's, with 0 spoken wrong.

## Step 0 result (2026-09-25): exact, in torch and on grilly2

**Built**
- `cubbyllm/model/grow.py` (`grown_meta`, `layer_map`, `grow_into`), pinned by `tests/model/test_grow.py` (10 tests):
  - Each of width ×2, depth ×2, FFN ×2, depth + FFN, all three, and depth ×3 gives the source's logits. Every parameter is randomised first, the zero-initialised adapter basis included.
  - The plain copy does not give the source's logits (the control).
  - The grown model's one-token decode agrees with its forward.
  - Every layer keeps its kind.
- `HybridBackbone(ffn_mult=…)`, default 2, byte-identical for every earlier checkpoint.
- `validation/grow_base.py`: grow, then score base and grown on the held-out tails, and optionally save.
- `validation/grow_parity.py`: the grown export on grilly2.
- `train_base.py` gains two environment variables:
  - `CB_FFN_MULT`.
  - `CB_INIT_FROM`: start from a checkpoint's weights at step 0 with a fresh optimizer; used only when there is nothing to resume.
  - The pilot needs no other code.

**Measured**
- Base checkpoint: step 21,103, float32 on the CPU.
- Scored on 6 held-out tails (arxiv, books, fineweb_edu, nemotron_code, unified, wikipedia) × 2 windows × 1,024 tokens.
- Logs: `validation/logs/grow_step0_*.{json,log}` and `grow_parity_*.log`.

|---|---:|---|---:|---:|---|
| depth ×2 + FFN ×2, zero exit | 1,292.6M | 2.63186 → 2.63186 | 1.1e-6 | 7.4e-4 | **exact** |

- **Reload.** Both exact models were saved and reloaded through `train_base.load_base` with the same loss. They were then exported with `export_base.py`; the export now frees the checkpoint before rebuilding the model, since the 7 GB width checkpoint had run out of memory.
- **On grilly2** (the local GPU), on 3 prompts (EN, FR, a question):
  - Grown torch vs grown grilly2: max |Δlogit| 5e-5 to 1.2e-4, the usual export parity; argmax agrees at every position.
  - Grown vs base, both on grilly2: **0.0** for depth + FFN (the new layers add exact zeros, so it is bit-identical) and ≤ 1.6e-4 for width; argmax agrees everywhere.

**Reading**
- Both grown shapes start exactly where the base is, in training and on the serving path.
- The plain copy starts 1.86 nats worse. That is the hole the pilot's arm 3 has to climb out of, against arm 2's zero-exit copy of the same shape.
- The grown checkpoints are kept off-repo for the pilot. On Colab the pilot can also grow from the base on Drive in seconds, which avoids uploading 5-7 GB per arm.
- **Next:** the pilot (§5), 4 arms × ~1 A100-hour. Two settings differ from the base run:
  - `CB_WARMUP≈50`: 300 warmup steps would be most of a 1-hour arm.
  - A new `CB_SEED`: seed 0 would redraw the base's own first batches.

## 6. What it brings to CubbyLLM

- **Capacity where the gates showed it runs short.** talk_v2 lost fact accuracy when fact records were diluted to 11% of the mix (H-E6), and v2.2's extra "don't say" records cost answers elsewhere. A bigger trunk gives talk, facts and program emission more room without re-balancing the mix every time. That is H-E10's step 5 at the base rather than the adapter.
- **No lost work.** The 16.8 A100-hours already spent are the first stage. The tokenizer, the host, the VM, the checks, the benchmarks and the data builders are all unchanged. Only the adapters are retrained, and that takes minutes.
- **Advantage over conventional models:** labs train each size from scratch, and a new model can be worse than the old one on day 0. Here the grown model starts exactly equal to the one that passed the gates. Every step after that is measured against the same gates, and it serves only if nothing gets worse. The knowledge still lives outside the weights, so growing buys language and reasoning room, not a bigger store to go stale.

## 7. Risks

- **Nobody has grown a MinGRU-style hybrid.** §3 is a derivation; step 0 checks the exactness, and the pilot checks the learning.
- **The base is annealed.** The re-warm is the published remedy (§4), with the forgetting it can bring caught by the replay and by the gates.
- **Decode latency.** Depth ×2 roughly doubles per-token latency on grilly2. If that matters for the voice path later, width ×2 is the shape to prefer at equal loss.
- **The control may win.** At 2.77B tokens the 450M has most of its data ahead of it. If it does win, the finding is still worth having: more data before more parameters.
- **Route C** (converting Qwen3-1.7B into our hybrid) stays out. It was left as Nick's call on 23 Sep (derived weights, and parametric knowledge in the weights).
