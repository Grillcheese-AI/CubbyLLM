# The harness, v0: one process that owns boot, state, the turn and the night (2026-09-28)

Status: SPEC + v0 built (`standin/harness.py`, pinned by `standin/tests/test_harness.py`, 12 tests on fakes). **Amended the same day by panel round 3** (`docs/research/2026-09-28-panel-round3-synthesis.md`): v0.1 replaces the store lock with store generations and two signing keys, makes speaking a ledger-first at-most-once effect, records the hormone state and generation id in every turn row, splits audit replay (100%) from regeneration replay, adds `gen_tokens` to the budget, a quarantine store with one `promote` tool, typed postconditions declared at frame creation, child permissions as an intersection, and world namespaces. The v0 code below is the substrate those land on; the sections it contradicts are marked. Source: Nick, 2026-09-28 ("we need some kind of bootstrap and an orchestrator, in fact the full system should act as an agent harness"), and the panel's two rounds (`docs/panel_fluent_harness.md`, `docs/panel_compiler.md`): six reviewers, one design, four of six said build this first. Pre-registered under **H-E14** in `CUBBYLLM_HYPOTHESES.md`.

## What it is

The parts exist as modules: the serving brain (`standin/serve.py`: sense → neurochemistry → route → a cortex), the verified ask loop (`standin/ask.py`), the event stream (`cubbyllm/reasoning/events.py`), the signed ledger (`standin/ledger.py`), the vault, the sleep cycle (`cubbyllm/reasoning/sleep.py`), the forge, the adapter bank. No one process owns boot, state, scheduling and the turn loop; the sleep cycle writes the stores that serving reads, with nothing between them.

The harness is that process. It adds no capability. It makes the existing ones one system:

- **boot** loads the stores, the VM and the adapters, runs the preflight against pre-registered gates, and refuses to serve if one fails;
- **the turn** is one typed step with budgets, every tool call through one registry, every spoken reply hashed into the ledger;
- **the night** is a job the same process schedules, and it holds the store lock while it writes;
- **replay** reconstructs any turn from the ledger and the stores.

The 450M model proposes (programs) and phrases (talk). It never decides what is true, whether a check passed, what a tool may do, what is written to a store, or whether to speak.

## One step

```
observe    the person's words, the sensors, the hormonal state; the context graph resolves "it"
route      the host's frozen tag router picks the turn kind (fact, chat, learn, help, plugin, task)
frame      a TaskFrame: kind, goal, allowed tools, budgets, status
plan       the emitter proposes (a program, a lookup); the disposer takes it only if it covers
call       each tool through the registry: permission, effect class, budget, then the call, then the ledger
verify     the VM's verdict per hop; the host's guards on the draft (name-and-number, value, claim, explicit gate)
act        speak, ask which one, or refuse; only what the verdict reached
record     the event stream, the ledger (a turn row with the reply's hash), the context graph, the day record
```

A multi-step task is a stack of TaskFrames under one root frame. A sub-frame is done when its own check passes (a VM verdict, a store read that returned), never because the model said so. The root frame's budgets bound the whole task.

## What stops a runaway

Every TaskFrame carries a `Budget`, spent by the registry as calls go through: `tool_calls`, `vm_hops`, `fetches`, `forge_attempts` (0 in a live turn), `depth`, `wall_s`. Exhaustion is a declared outcome (`status = "exhausted"`, spoken as "I ran out of steps on this"), never a silent truncation. Repeated failure of the same step ends the frame. Defaults for v0 (the owner's to move): tool_calls 8, vm_hops 64, fetches 1, depth 3, wall 10 s.

## Tools

A tool is declared, not discovered: `Tool(name, effect, needs, fn, doc)`.

- `effect` is one of `read` (a store lookup, a VM run without writes), `propose` (something that may become a write after a gate: a fetched fact, a forged program), `write` (a store write, a memory write). Effect classes are enforced **at call time** by the registry, not only at certification: two certified tools whose composition writes are caught here.
- `needs` is the set of permissions a call requires (`read_history`, `read_wiki`, `vm`, `fetch`, `write_store`, `vault`, `explicit`, `forge`, `plugin:<name>`). **Deny by default:** the frame's `allowed` set is what the turn kind grants, and a tool whose `needs` is not a subset is refused before it runs. The chat kind never gets `write_store` or `fetch`; a live turn never gets `forge`; `vault` is never granted to a talk tool.
- Every call, allowed or refused, is a ledger row: tool, effect, the arguments' hash (the arguments themselves through the vault when they may hold a person's words), the outcome, the frame and turn ids.

The tools of v0 wrap what exists: `history.lookup` (history_lookup), `wiki.facts` (the wiki world), `vm.run` (cubelang_client.run_program_proto), `learn.fetch` (learn.py's fetch, effect `propose`), `store.write` (a gated write, effect `write`), the plugins' `handle`. Their bodies do not move; the registry is the one door.

## Boot

```
1. read the signed config: thresholds (τ_vm, τ_ret, the floors and margins), the model and adapter hashes, the gate pack
2. open the stores read-only; check each store's integrity hash against the config
3. start the VM (run-proto, resident); run its self-test
4. load the base and the adapters; check their hashes against the config
5. run the preflight: the gate pack (a fixed set of asks with expected outcomes: fact families, absent, a
   contradicting-context capital, an explicit request that must be refused, a wrong-answer sentinel that must
   not be spoken); the pass rates must meet the pre-registered bars
6. open the stores read-write; open the ledger; serve
```

**Thresholds are never recalibrated at boot.** They are read from signed config; the preflight passes or the process refuses to serve. A boot that could lower a threshold to pass its own test is a hole (the panel's word). Calibration is an offline job whose output is a new signed config.

Refuse to serve if: any store hash differs, the VM self-test fails, an adapter hash differs, the ledger cannot write, or any preflight bar is missed. The refusal is itself a ledger row.

## The night

*(v0; replaced in v0.1 by store generations with an atomic manifest swap — see the synthesis. The lock as built would stall serving for the night's whole run and leaves the config's store hashes stale after every night.)* The sleep cycle (`cubbyllm.reasoning.sleep`) runs as a job the harness schedules, in the same process or a child it owns. Before it writes (consolidated facts, episodes, skills, the adapter training set), it takes the **store lock**; a turn that arrives while the lock is held is answered from the read-only view or asked to wait, never served from a store mid-write. Nothing the night writes changes what may be spoken: a consolidated fact is looked up and verified like any other; a promoted adapter is a new hash in a new signed config, loaded at the next boot.

## Where the model sits, and what the harness never lets it decide

Two roles, two adapters, both behind the emitter interface: the program emitter proposes CubeLang (verified before it runs); the talk adapter phrases what the verdict returned. The harness never lets the model decide: whether a fact is true; whether a hop cleared τ; which tool runs, or with what permission; what is written to a store; whether content is allowed; whether to speak after a failed check; which event a pronoun means when the context graph and the host disagree. It may propose and rank; the host disposes.

## Bootstrap in the second sense: a capability from almost nothing

Cubby-Man is the pattern: two facts, every move VM-mediated, refused moves become walls, hypotheses kept apart from facts, power-moves invented and certified. The harness generalises it as four stores per capability — observed facts, hypotheses, verified skills, episodes — and one promotion rule: a hypothesis becomes a fact only by a verified observation; a skill is promoted after N successes across distinct contexts (N pre-registered per world). The arbiter's reward-prediction error reorders proposers; it never writes.

## v0: the smallest version, built 2026-09-28

`standin/harness.py`:

- `Tool`, `ToolRegistry` (deny by default, effect classes, budgets, every call ledgered);
- `Budget`, `TaskFrame` (a stack per turn);
- `Preflight` (a gate pack from JSON; bars; refuse-to-serve);
- `Harness`: `boot()`, `turn()` (wraps the existing `CubbyBrain.turn` and `AskLoop.ask`; hashes the reply into the ledger), `replay(turn_id)`, `night()` (the sleep cycle under the store lock);
- `standin/data/gate_pack.json`: the preflight asks.

Not in v0: the multi-step DAG (the stack is there; only single-frame turns are wired), the forge in the loop, the event stream's panel showing frames, plugins' permissions beyond `plugin:<name>`.

## Gates (pre-registered; the numbers are the owner's to move)

1. **Same answers.** On the H-E6 fact families and the E8/E9 test splits, the harness's answers equal the modules' (byte-identical replies on the same draw): the harness adds no capability and loses none.
2. **Every spoken reply has a ledger row** with its hash, its frame and its verdicts: 100%.
3. **Refuse-to-serve on injected faults.** Corrupt each in turn — a store hash, an adapter hash, a threshold in the config, the VM binary, the ledger path — and boot must refuse in 5 of 5, with a ledger row naming the check.
4. **Replay.** *(split in v0.1)* Audit replay — the recorded model outputs and the deterministic host — reproduces the reply hash for 100% of 200 turns from their pinned generation, hormone state and inputs; regeneration replay (re-decoding on the engine) is reported apart, as a property of the engine.
5. **Deny by default holds.** A probe set of 50 calls that a turn kind must not make (chat writing a store, a live turn forging, a talk tool reading the vault): 0 executed, 50 ledgered as refused.
6. **Kill and restart.** *(reworded in v0.1: speaking is ledger-first, at-most-once)* Kill the process at every transition, 100 times and more: 0 replies spoken without an intent row, 0 spoken twice, every orphan intent resolved on restart, the same store generation after restart.
7. **Latency.** p95 of a fact turn ≤ the modules' + 20%.

**Kill:** if gate 1 fails, the harness changed an answer and is not a harness; if gate 2 or 3 fails, it is plumbing, and says so in the report.

## What it brings to CubbyLLM

- One owner of state: the store-write race between the night and the day is closed by the lock.
- One door for tools: deny-by-default with effect classes at call time, so a certified program cannot compose its way into a write.
- Every answer replayable from the ledger: the audit the design promised becomes a command.
- The seat the adapter lifecycle's promote rule and the branch runner (D) both need: budgets, frames, the ledger.
- **Advantage over conventional agent frameworks:** they let the model call tools and judge its own results; here the model is a proposer behind a registry, the VM is the judge, the ledger is the memory of every decision, and a boot that fails its own gates does not serve.


## v0.1, built 2026-09-29: the nine round-3 changes, and the harness on the serving brain

`standin/harness.py` (pinned by `standin/tests/test_harness.py`, 30 tests) and `standin/harness_wiring.py`
(pinned by `standin/tests/test_harness_wiring.py`, 7 tests, on a brain shaped like `CubbyBrain`). Uncommitted.

What changed, against the round-3 list:

1. **Store generations, not a lock.** `Generations`: the night writes `gen_<n+1>/` beside `gen_<n>/` and never
   touches it; the boot pack runs against the candidate through `brain.view(stores)`; on a pass the manifest is
   signed with the **harness key** and swapped by one atomic rename, and the brain switches; on a fail the
   candidate stays on disk as rejected and the current generation keeps serving. Every frame pins the generation it
   started on and the row names it. Two keys: the **owner's** signs the config (thresholds, gate packs, adapters,
   the live emitter) and never a manifest; the harness's signs manifests and never a config. The v0 lock is gone
   (test: a turn during the night is answered from g). v0's owner-signed store hashes still boot a deployment
   without generations.
2. **Speaking is an effect, ledger-first, at-most-once.** `intent(turn, reply_hash)` is a row before the bytes
   leave through `speaker(rec)`; `spoken` after. A crash between the two leaves an orphan that `recover()` resolves
   at the next boot as `interrupted` -- never re-spoken; turn ids continue the ledger's so a restart never reuses
   one. Gate 6 is now: 0 replies without an intent row, 0 spoken twice, every orphan resolved.
3. **Everything that bends a turn is in its row:** the hormone vector at turn start, the generation, the context
   delta, the adapter and live-emitter hashes, the decode seed; the model's verbatim outputs go to a vaulted
   `model` row. `replay(turn, "audit")` runs the recorded outputs through the deterministic host (`brain.replay`)
   and must reproduce the reply hash (test: 20/20, and still 20/20 after the engine "drifts");
   `replay(turn, "regen")` decodes again and is reported apart. `hormone_gate()` runs the boot pack at hormone
   extremes: the same spoken values, and no extreme widens a grant (a rule in the config may only `drop`).
4. **Typed postconditions, declared at creation** (`TaskFrame.post`: answer / learned / phrase / consolidated) and
   judged by the host (`judge`): a task reply without a verdict is `failed`, not spoken. An empty tool result is a
   return (`ok ... empty` in the row), never the frame's success. A child frame's grant is the intersection of its
   parent's and its kind's, a tree by construction.
5. **Budgets include `gen_tokens`** (the emitter's `max_new_tokens` is capped to what is left; nothing left is
   `exhausted` before the model runs) and the lines a real turn spends apart: `reads`, `vm_runs`, `vm_hops`,
   `fetches` (2: refuse -> fetch -> a second walk), `tool_calls` for the rest. `Budget.vm()` maps the frame onto the
   VM's `Budget` (vm_hops -> max_jumps, the wall's remainder -> max_wall_ms, config max_ops / max_queries).
6. **Quarantine and `promote`.** A `propose` tool's result is quarantined and comes back as `{proposal, value}`;
   `promote` (effect write, night only) is the one path into a store. `fetch` is an `external` effect, off for
   fact / chat / help whatever the grant. Native VM modules a program `use`s are declared with effect classes
   (`vm_modules` in the config) and checked per call; the harness SETS a program's `budget` and, when the
   generation carries one, its `knowledge_path` -- the caller's values are dropped and the row says `harness_set`.
7. **Worlds are namespaces.** `Fact(text, world, status, valid_time, provenance)`; status in observed / asserted /
   hypothetical / counterfactual / derived; a counterfactual or hypothetical lands only in a `branch:` world; a
   frame may be limited to the worlds it can write.
8. **The gate pack rotates** (`standin/data/gate_pack.json`): `boot` (small, blocking, run at boot and on every
   candidate generation), `regression` (offline), `sentinel` (held out; `exclude_from_harvest` keeps it out of the
   sleep cycle's material). Boot refuses a `boot` pack that lacks the three real defects: a contradicting context,
   an absent role, a verified program answering the wrong role.
9. **The live emitter fits the card or nothing serves.** `emitters.live.params_m` against `max_live_params_m`
   (600) is a boot check; the 2.6B stand-in is `emitters.teacher`, reachable only through a `teacher` grant, night
   only.

**Wired to the serving brain** (`harness_wiring.wire(brain, harness)`), without changing an answer: `brain.worlds`
becomes gated stores (a query inside a turn is `store.read`, an `add` is `store.write`; lookup, texts, index,
`in` pass through), `cubelang_client.run_program_proto` inside a turn is `vm.run` with the frame's budget
(resume flows through it), `emitter.emit` spends `gen_tokens`, and the harness senses and routes once outside
the frame (`CubbyBrain.sense`, `turn(route=, sensed=True)` -- the brain's own order, appraisal -> hormones ->
route) so a chat turn reads no store. Outside a turn every door passes through untouched. Test: seven turns
(fact, chat, learn, help, a refusal, an absent subject, a repeat) byte-identical to the unwired brain with the
same hormone trajectory; inside a task turn the ledger holds `store.read` then `vm.run` with `max_jumps` from
the frame; a chat turn's only row is its ASK; a program that `use`s an undeclared module is refused; a caller's
budget never reaches the VM.

**Gates now measured on fakes:** refuse-to-serve 8 of 8 injected faults (v0's five plus a manifest signed with
the wrong key, an over-cap live emitter, a boot pack without the defects); deny probes 500 of 500 refused and
ledgered, 0 executed; the absent-role probe in every boot pack; audit replay 20/20. **Still the owner's to run on
the real brain:** gate 1 (byte-identical E6/E8/E9 replies -- the wiring's construction says yes; the run says),
latency p95 <= the modules' + 20%, and the pre-registered "no budget binds on the gate-1 sets".

**On the serve path:** `serve_api --harness [config.json]` boots the brain through `harness_wiring.boot_serve`
after every plugin is mounted (so their doors are behind it too): an owner-signed config's path, or bare for
the dev shape -- a config signed here with the vault's `harness-owner` subkey from the brain's own thresholds,
the adapter files it was started with and a boot pack DERIVED from the store (`derive_packs`: for three of
its template facts, the fact itself, an absent role on its subject, a contradicting context, the relation on
an unknown subject -- the three defects, in the store's own words; `standin/data/gate_pack.json` is the
deployment template with the same shape). A failed check prints the refusal and exits 3; `POST /turn` then
runs `harness.turn`, and every reply carries `turn_id`, `ledger`, `status`, `generation`, `spoken`.

**Not in v0.1:** the night's real `night_fn(dst, n)` (the sleep cycle writes in place today; the harness runs
it in place and ledgers it until then), the fetch door for plugins, the vault of the person's words at the
speak boundary beyond the ledger's, the owner's key held anywhere but this machine.

## First live boot, 2026-09-29: the gate refused, and it was right twice

`serve_api --harness` on the real brain (v12e programs, v10t talk, wiki world, ask loop, cubby-man) refused
to serve: `preflight` failed `absent_role` 0/3 and `contradicting_context` 0/3 (fact 3/3, wrong_role 3/3,
small_talk 1/1). The replies behind it held two different problems:

1. **A harness miscount (5 of the 6 failures).** The brain answered those asks with its dont-know line, but the
   record carried no marker, so `_spoken_rec` counted the refusal as speech. Fix: `CubbyBrain.turn` now sets
   `rec["dont_know"]` on every cortex (reply == the dont-know line, or the chat path's `spoke_safe`).
2. **A real brain defect (1 of 6, and far more off the pack).** "What is the anthem of kozjaty?" was spoken
   "Track (song)": a one-hop answer was held only to "is the object of an offered fact", so a flat hit on
   another relation, or another subject, grounded it. Fix (`serve.py`, `tail_matches`): for a one-hop parsed
   question the grounding fact must be the tail's relation (word Jaccard >= 0.6) OF the tail's subject.

Measured on the store's own questions (200, flat fallback on, one GPU pass; the gate only flips grounded
true -> false, so before = after + the turns where `gate_tail` fired):

| set | before | after |
|---|---|---|
| positives (200): correct / wrong / dont-know | 147 / 6 / 47 | 146 / 3 / 51 |
| one-hop positives (104) | 90 / 3 / 11 | 89 / 0 / 15 |
| multi-hop (89), unparsed (7) | unchanged | unchanged |
| absent role on a one-hop subject (91): spoken | 56 | **0** |
| the same relation on an unknown subject (91): spoken | 67 | **0** |

One correct answer lost (a two-hop question the grammar parses as one hop), three wrong ones silenced, and the
absent-role / unknown-subject confabulation rate goes from 62% / 74% to 0 on this store. The serve selftest
(28 val chains) was 25 correct / 0 wrong / 3 dont-know before the change. Pinned by
`test_tail_matches_holds_the_relation_and_the_subject` and
`test_live_one_hop_absent_role_is_not_spoken_and_is_marked_dont_know`. What the boot gate is for: it found a
defect the selftest (all positives) could not see.
