Status: draft, 2026-07-23, revised same day. This is a pre-registration of falsifiable hypotheses, not a design doc. Nothing here is a commitment to build anything — it's the accumulated research and concept-survey material from the CubbyLLM planning phase, organized so each claim can be checked before engineering time gets spent on it.

See Section 1 and the rewritten Group C.

## 0. How to use this document

Every hypothesis below follows the same shape: a claim, why we currently believe it (which source it traces back to), a concrete way to check it, and what result would kill it. A hypothesis with no kill criterion isn't really a hypothesis — it's an opinion — so every entry has one even where it's approximate. Status is one of **VERIFIED** (independently reproduced this session, not just asserted by a source document), **PLAUSIBLE** (a real source claims it, mechanism makes sense, but nobody has measured it against Cubby's actual code), or **SPECULATIVE** (asserted in a vision/blueprint document with no implementation behind it at all).

Hypotheses are grouped by the two structural problems driving the redesign (memory/forgetting, VSA binding head), then by the two halves of the one-line goal (fast/profitable, automatic specialization), then backbone and hardware, then a small set of organizational hypotheses, then training-data findings. Section 10 gives a suggested validation order — cheapest and most falsifiable first, hardware last.

## 1. Context

**Goal (one-liner):** Fast and profitable LLM gen 2 hybrid — general tasks plus specialization, automatic.

CubbyLLM is the redesigned successor to `cubby-lm`, drawing on lessons from `cubby-lm` and its environment sibling `cubemind`. Two concrete problems motivate the redesign, both already scoped by the user:

**Problem 1 — VSA binding head.** Cubby's current `VSABindingHead` operates over a frozen D=10240 codebook. **Corrected 2026-07-23 (validation campaign):** the dict-lookup `UNBIND_ROLE` this paragraph previously attributed to the binding head actually lives in **cubemind's VM** (`reasoning/vm.py:602-606`) — `vsa_binding_head.py` contains no unbind mechanism at all; it is a clean cosine-readout output head. The real-unbind gap is real but sits on the VM/reasoning side; the binding-head work for CubbyLLM is a from-scratch build either way (see H-B3, H-B5).

**Problem 2 — Hebbian memory layer.** The current Hebbian/Oja-style memory update is detrimental to memory: it drifts and forgets catastrophically under sequential learning. This needs fixing using the research summarized in Section 3.

**Structure — two different axes, kept deliberately separate.** CubbyLLM's *package/directory layout* will likely mirror cubemind's — meaning cubemind's intended, documented structure, not its accumulated sprawl (see Group F). CubbyLLM's *model architecture* is a different question entirely: **CubbyLLM is an entirely different structure than cubby-lm, built from scratch, including the vocabulary** (correction, 2026-07-23). cubby-lm's trunk is prior art — informative about what worked, what didn't, and what to avoid repeating — not a frozen substrate CubbyLLM has to sit on top of. Nothing below should be read as "patch cubby-lm's trunk"; where a hypothesis references cubby-lm's actual code, it's diagnosing the predecessor to inform a fresh design, not scoping an in-place edit.

**New, explicit requirement (2026-07-23): a much larger vocabulary than cubby-lm's 32k, unlocked specifically by removing the full-vocabulary softmax step.** The causal order matters and is worth stating precisely: vocab size is being treated as a variable that gets freed up once the output/embedding mechanism stops paying an O(vocab) cost per step — not a number chosen first that then needs optimizing around. This promotes what was previously framed as a set of possible efficiency optimizations (old Group C) into a load-bearing design requirement; see the rewritten Group C below, including two new hypotheses (H-C6, H-C7) this requirement surfaces.

cubby-lm's own shape, kept here for reference and lessons-learned, not as a CubbyLLM constraint: d_model=2560, n_layers=22, d_ffn=6848, tokenizer `grillcheese_spm32k_v2` (32k SPM, frozen in cubby-lm), MinGRU recurrence per `HybridBlock` with optional MoE / sliding-window attention / `EpisodicMemory` / SwiGLU FFN. `SegmentMemory`, `MTP`, and `CubeLangHead` exist as code but are not wired into the default forward pass — `CubeLangHead` is self-labeled "SCAFFOLD." Worth carrying forward deliberately rather than repeating by accident: the value of gating each new capability behind an explicit version flag, and the risk of building attachments (MTP, CubeLangHead, SegmentMemory) that never get wired into the actual forward path.

**Training data (added 2026-07-23):** a real, substantial corpus (~210GB) exists at `D:\grillcheese_training_data` — the user's own framing was that it can be used both for testing and as raw material for "a better dataset." Full findings are in the new Group G below, but the single most consequential discovery deserves a mention here: a training-data-generation script in this folder revealed an already-existing, already-in-production VSA/hyperdimensional-computing implementation (`grilly.experimental.vsa.ops`) running at the exact same D=10,240 dimensionality as both cubby-lm's binding head and cubemind's world-arena block-codes. That's not yet confirmed to be the same substrate, but it's a strong enough lead that it now sits at the top of Group B's validation order (H-B5), ahead of the two candidates the earlier survey found.

## 2. The central bet (H0)

**Claim.** Context-conditioned, hypernetwork-style parameter generation — making a model's active weights a function of context, θ=f(c), rather than a fixed state that gets overwritten in place — is simultaneously the fix for catastrophic forgetting *and* the mechanism for automatic specialization. If true, the two halves of CubbyLLM's one-line goal ("general tasks" and "specialization automatic") collapse into one underlying mechanism rather than two separate subsystems.

**Why we believe it.** Three independent sources converge on this same shape, which is a stronger signal than any one of them alone:

The Gradient Context Encoder (GCE) work (Ran Cheng, "Context Channel Capacity") argues catastrophic forgetting is mathematically forced whenever a state-based learner runs at C_ctx=0 — i.e., whenever weight updates don't structurally depend on context — and that the fix is making θ an unbypassable function of context, f_GCE(c), verified by Wrong-Context Probing (P5) so the context signal can't be optimized away in training (the "Structural Bypass Defect"). This closed a CIFAR-10 oracle gap from 23.3pp to 0.7pp in the source material.

Sylph, independently, replaces global softmax classifiers with sigmoid-decomposed binary classifiers whose parameters are generated by a few-shot hypernetwork conditioned on task embeddings — explicitly to avoid global gradient interference and prevent forgetting during sequential task adaptation. Same shape (hypernetwork generates params from context), different framing (classifier heads, not general weight rectification).

Dragon Hatchling (BDH) arrives at a related idea from the architecture side: its `bdh-cl` continual-learning extension pairs fast local Hebbian plasticity with mechanisms to keep it from drifting, and the broader "trillion-parameter blueprint" research (Section 6) explicitly proposes a GCE-style controller as the piece that prevents BDH's in-place Test-Time-Training fast weights from drifting.

**What's notable:** none of the four surveyed sibling folders (cubby-concepts, AURA_GENESIS, GrillCheese, Novel_GNN_Arch) implement this pattern anywhere. The closest analog is AURA_GENESIS's Liquid-MoE `tau(x)`-conditioned continuous-time gating cell (`aura/core/liquid_moe.py` — real, working, NumPy-only), which is *routing* (selecting among fixed experts) rather than *generating* continuous parameters, but is a plausible template for the small controller network that would emit the context embedding driving a hypernetwork. This means H0 is genuinely new work for CubbyLLM, not something to import — everything downstream in Groups A–D is really this one bet applied to different parts of the model.

**A fourth independent instance, added 2026-07-23:** generating token embeddings from context instead of storing them in a static lookup table (Group C's H-C1/H-C3, now driven by the much-larger-vocabulary requirement in Section 1) is itself a specific case of H0's mechanism — θ_embedding = f(token/context) rather than a fixed embedding matrix. The vocab requirement and the forgetting fix aren't two unrelated bets that happen to share a document; they're two applications of the same underlying idea, this time one driven by a hard product requirement rather than a research paper. That's a reason for more confidence in H0, not less.

**How to validate.** Build the smallest possible GCE-style controller (a context embedding feeding a rectification to one small weight block, not the frozen trunk) and run the P5 Wrong-Context Probing protocol against it, plus a toy sequential-task retention benchmark, compared against a frozen-weight baseline and the current Hebbian layer.

**Kill criterion.** If P5 probing shows the context signal gets optimized away even after architectural hardening (the Structural Bypass Defect resists the standard countermeasures), or if the added hypernetwork forward/backward pass erases the "fast" half of the goal at the scale CubbyLLM actually needs, the central bet needs revision — not abandonment, but a scaled-down or partial version (e.g., gating only specific memory slots rather than general weight generation).

**Validation result (2026-07-23 campaign): SUPPORTED at toy scale, with one load-bearing caveat.** The smallest θ=f(c) prototype (frozen backbone per this section's own protocol, hypernetwork-generated head, 6 sequential tasks, no replay) shows near-zero forgetting **only with architectural hardening** (von-Oswald-style output regularization): task-0 MSE 0.062→0.060 across all tasks, P5 right-ctx 0.06 vs wrong-ctx 1.87 (context load-bearing, no bypass). The **naive** hypernetwork without hardening ends *worse than the fixed-weight baseline* (2.734 vs 1.778 final MSE) — the hypernetwork's own shared weights are themselves a C_ctx=0 learner and interfere internally, and its P5 probe flags bypass. So H0 is only ever "generation + anti-drift countermeasure," never naive generation. Cost: 4.1× baseline per step at toy scale, growing with number of protected contexts — the "fast"-half kill clause stays open at scale. `VALIDATION_REPORT.md` / `validation/exp_h0_gce.py`.



**A WORKING theta=f(c) IMPLEMENTATION ALREADY EXISTS — found 2026-08-02 in cubemind, port it rather than rebuild.** `cubemind/execution/mindforge.py` (452 lines) is real, runs, and has full analytic gradients: `MindForge.forge(context, layer_id) -> (A, B)` at L302, `forge_with_cache` L309, `backward(d_A, d_B, layer_id, cache)` L358. Its parameterization is the one CubbyLLM should adopt: a block-code hypervector context is projected `W_proj (d_hidden, k*l)`, LayerNormed, concatenated with a per-layer embedding `layer_embeddings (n_layers, d_hidden)`, pushed through an MLP to `W_coeff (n_basis, d_hidden)`, and the generated adapter is a **linear combination of learned low-rank bases**: `A = sum_i coeffs[i]*A_basis[i]`, `B = sum_i coeffs[i]*B_basis[i]`. Verified by execution — gradients populate all 10 parameters, and it is genuinely conditioned on both inputs (layer sensitivity |A(ctx,L0)-A(ctx,L1)| = 2.30; context sensitivity |A(c0,L0)-A(c1,L0)| = 67.15). It is correctly wired into `cubemind/training/vsa_lm.py::VSALayer` (L877 forge, L921 the analytic backward). **This matters because CubbyLLM's own `HyperGenerator` generates a full d*d matrix (ctx_dim=32 -> 4.19M outputs, ~134M params) which will not scale**; the basis-coefficient form is roughly 40x smaller and generates *per-layer* adapters. Two caveats: the GPU path is dead (`_mindforge_gpu_ok()` checks for `mindforge_basis_mix`/`mindforge_bwd_coeff`/`mindforge_bwd_basis` in grilly_core, which do not exist, so everything runs numpy `tensordot`), and there is a stale duplicate `mindforge.patch.py` encoding a removed-softmax design that `harrier_pretrain.py` was written against — that trainer hand-rolls approximate gradients, never calls `forge.backward()`, and has produced no checkpoint. Take `mindforge.py`, not either of those.

**The torch port that exists is DEGENERATE — this is the live gap between the bet and the code.** `cubemind/model/cubby/heads.py::MindForgeLoRAHead` (L17) claims to be a "PyTorch port of cubemind.execution.mindforge" but drops the two things that make it theta=f(c): there is **no layer embedding** (it is per-head, not per-layer) and **no VSA input** (context is a plain dense vector). Worse, it is self-conditioned in every call site — `MinGRUMultiTask.forward` L272 calls `head(pooled)` with `context=None`, and L86-87 then assigns `context = x`, with the default head spec declaring `"task_code_source": "self"`. So in practice it computes **theta = f(h)**, conditioned on the model's own pooled hidden state; no external task/context signal crosses into it at all. The `context=` argument is plumbed and nothing supplies it. Also `basis_B` is zero-initialised there (L80) while the numpy version uses small-random (L243) with the explicit comment "Zero init kills gradients through the LoRA path" — the two implementations contradict each other on their own core design point, so the torch LoRA path may not be training.

## 3. Group A — Memory & forgetting fix

**H-A1 — Diagnosis: the Hebbian layer fails because it runs at C_ctx≈0.** The Impossibility Triangle (zero forgetting + online learning + finite parameters can't all hold for a state-based learner) predicts this. Status: **VERIFIED (2026-07-23 campaign, both halves)** — structurally, the real `HebbianGrowthLayer` update is dW = f(x, xWᵀ, W) with no context input existing anywhere in its signature or update path, so C_ctx = 0 *by construction* (no estimation needed); empirically, after learning a task to EV 0.97 the shared basis retains EV 0.06 (**forgot 94%**) after three subsequent tasks; neurogenesis mitigates to 72% forgotten but doesn't rescue. Two incidental findings: the layer's default `nonlinear` (y³) mode never tracks subspace structure under a reconstruction metric (only `sanger` mode learns), and its residual metric becomes unreliable (EV>1) once grown bases decorrelate. See `VALIDATION_REPORT.md` / `validation/exp_a1_drift.py`.

**H-A2 — GCE-style generation removes catastrophic forgetting in CubbyLLM's memory layer.** Status: **toy-scale VERIFIED in the hardened form** (2026-07-23 campaign — see H0's validation result above for the numbers; the toy experiment *is* this hypothesis's specified side-experiment). Kill criterion checked and not triggered: bypass did not survive hardening. Still open at scale: the hardening cost curve and whether the mechanism stays scoped to the memory pathway in a real model — the second kill clause is untested until there is a real network to scope it in. `validation/exp_h0_gce.py`.

**H-A3 — A Sparse Distributed Memory substrate is more forgetting-resistant than dense Hebbian updates, purely by construction.** Source: `cubby-concepts/vsa/sdm.py` — real code, independently verified this session (staged the files, ran `pytest` directly: 61/61 tests passed, 81.6s wall time). Verified recall: 100% accuracy (1000/1000, cosine similarity 0.9957) at M=D=10000 with 1000 stored associations. Each write spreads across roughly 40 of 10,000 hard locations (calibrated Hamming radius) instead of overwriting one dense weight matrix — the standard SDM graceful-degradation argument versus Hopfield-style catastrophic collapse. Status: **the mechanism is VERIFIED; the forgetting-resistance property itself is PLAUSIBLE, not proven** — the cubby-concepts repo has no test that pushes the SDM toward/past capacity or compares its degradation curve against a Hebbian baseline. The repo's own CLAUDE.md names a "Zero-Forgetting Stability Benchmark" but it doesn't exist as code anywhere — file, function, or test. Also note: the repo proves the CLAUDE.md-specified Hamming radius of 4500 bits is actually broken (activates ~0 locations at full dimension) and ships a regression test for that fixed bug — a good sign for the code's honesty, a reminder to use the calibrated radius, not the originally-specified one. **Validate** by building that benchmark (it doesn't exist yet) and running it against SDM and the current Hebbian layer side by side.

**Validation result (2026-07-23 campaign): the benchmark now exists (`validation/exp_a_forgetting.py`) and the answer is split.** At matched state (~D² numbers each, D=2048, SDM M=D, online single-pass): SDM is the **only order-agnostic candidate** — at N=1024 its recall is ~15% uniformly across write order, while every dense method is recency-biased or totally collapsed (pure Hebbian: 0% for old AND new — overload destroys everything). That's the "graceful by construction" half, CONFIRMED. The capacity half is REFUTED at parameter parity: SDM's curve (99%→77%→15% at N=128/512/1024) sits below NLMS (100%→100%→51%) — the famous 100%@1000 cubby-concepts result used M=D=10000, ~5× the state per stored pair. SDM buys *fairness*, not *capacity*. Status: mechanism VERIFIED, blanket forgetting-resistance claim now has honest boundaries.

**H-A4 — NLMS is a cheaper drop-in replacement than a full hypernetwork rewrite.** Source: `AURA_GENESIS/aura/core/nlms.py` — real, complete, ~14KB, textbook Normalized LMS (`w ← (1−l2)·w + mu·(e·x)/(‖x‖²+ε)`), extended with group-sliced per-feature learning rates, a prosody-style gate, and dead-zone guards that skip updates when the prediction is already close enough. NLMS is error-corrective and self-normalizing by input energy, which classical adaptive-filter theory uses to bound weight drift — a real structural advantage over raw Hebbian/Oja. Status: PLAUSIBLE, with an important caveat surfaced by the AURA_GENESIS survey: AURA's actual anti-forgetting strategy is not "a smarter shared update rule," it's hard parameter isolation — one private linear head per domain/realm (88 domain files + ~150 realm files under `svc_nlms_weights/`), created on demand and never shared across concepts. That sidesteps interference by construction, not through NLMS's math, and doesn't obviously transfer to a shared dense memory layer where isolation isn't an option. **Validate** by swapping Oja for NLMS in one memory update path and rerunning the same forgetting benchmark as H-A3, in a setting where weights are actually shared (not per-concept-isolated) — that's the setting AURA_GENESIS never tested.

**Validation result (2026-07-23 campaign): SUPPORTED in exactly that never-tested shared-weight setting, with its failure mode now named.** In the H-A3 benchmark, matrix NLMS posts the best capacity curve of every candidate (100% recall through N=512, 51% at N=1024, graceful decline, no catastrophic cliff) — clearly better than pure Hebbian (cliff to 0% at 1024) and *vastly* better than the flat-decay Hebbian production form (65.6% already at N=128, worst curve measured). The cost: strongest recency bias past capacity (write-order quartiles 0/11/93/100 oldest→newest) — NLMS forgets oldest-first, LRU-like. As a cheap upgrade over Oja: yes. As zero-forgetting: no. `validation/exp_a_forgetting.py`.

**H-A5 — An external episodic store can complement, not replace, a fixed weight-based memory layer.** Source: GrillCheese's `capsulememoryintegration.md` (833 lines, full read) — a hippocampus-inspired design: Dentate-Gyrus-style sparse expansion (32D→128D, ~2% top-k winner-take-all) feeding CA3-style FAISS pattern completion, with importance-scored eviction (`score = consolidation_priority · stability · (recency + log(access_count))`, top 80% kept, protected items never evicted). STATUS.md corroborates a running instance (97 memories stored). This is architecturally a complementary-learning-systems split (fast episodic store outside the weights + slow weight-based consolidation), the same philosophy as Memorizing Transformer/MemGPT — it never touches synaptic plasticity at all, so it's orthogonal to, not competing with, the Hebbian fix. Status: PLAUSIBLE as a complementary mechanism, not a fix for the underlying problem. One documented weakness: the residual-stream injection hook (tiling a 32D vector across a 3072D residual stream with no learned up-projection) is methodologically weak; the text-context injection half is more credible. **Validate** by prototyping the DG-style sparse-expand + pattern-completion step as a side channel and measuring whether it reduces pressure on the weight-based memory — explicitly not a substitute for fixing that memory.

**Validation result (2026-07-23 campaign): mechanism VERIFIED at toy scale.** DG-style expansion (8× up-projection, 2% WTA) over a Hebbian store, with a *size-matched dense control*: at N=512 associations both dense variants collapse to 0% recall while the sparse code holds 100% — pattern separation, not parameter count, buys ~2× capacity (its own cliff arrives at N=1024). Also observed: dense Hebbian fails as a cliff (100%→0% between N=256 and 512), not a graceful curve. Complement framing confirmed. `validation/exp_a5_sparse.py`.

**H-A6 — Negative-result flag: no sibling folder has a validated fix for this problem.** All four surveys converge on the same finding. GrillCheese's own production Hebbian layer (`grillcheese/backend/brain/gpu_brain.py::hebbian_update`) implements `ΔW = η·⟨pre⊗post⟩ − λ·W` — a flat decay term, not true Oja normalization (no `post²·W` term, no norm-convergence guarantee) — the same failure class CubbyLLM is trying to fix, with a documented live shape-mismatch bug in the same function. Its own `forreview/capsules/DECISION.md` lists "Add EWC for continual learning" as still-open future work. Grepping GrillCheese's entire `learning/` package turns up no EWC, no orthogonal projection, no replay-based consolidation — only a crude activation-threshold "neuronal growth" heuristic, loosely adjacent to SPHeRe's structural-projection idea but untested against it. Novel_GNN_Arch's closest analog, `apply_outcome_update()` (importance-gated plasticity — a per-memory-slot effective learning rate driven by a plasticity trait and a simulated reward-prediction-error signal), is a well-shaped design sketch conceptually close to Elastic Weight Consolidation applied at memory-slot granularity, but it's ~250 lines of hand-tuned, duplicated-across-two-files demo code, tested only on 2–10 hardcoded synthetic records with randomly sampled (not task-derived) outcomes — zero quantitative forgetting-benchmark evidence either way. **Conclusion, not really a hypothesis: CubbyLLM cannot shortcut this problem by importing a sibling's solution. Budget real R&D time and benchmark every "reuse" candidate rather than adopting any of them on faith.**

**Validation result (2026-07-23 campaign): every sub-claim fact-checked by direct file reads and CONFIRMED**, with three precision fixes: GrillCheese's flat-decay update is at `gpu_brain.py:376` exactly as described, but the documented shape-mismatch bug is filed against its *caller* (`unified_brain.py::_update_hebbian_weights`, per `gcheese-faiss/CRITICAL_ISSUES.md:104-110`), not `hebbian_update` itself; `apply_outcome_update()` is ~38 lines duplicated across two files (not ~250 total); and the nuclear-test demo uses fixed ±0.8 outcomes — only the extended demo randomizes. Zero grep hits for EWC/elastic/orthogonal/replay/consolidat/fisher across GrillCheese's `learning/` package, and `DECISION.md:241` lists EWC as future work, both confirmed verbatim. The negative result stands at full strength.

## 4. Group B — VSA binding head fix

**H-B1 — cubby-concepts' `vsa/core.py` + `vsa/resonator.py` is usable as CubbyLLM's binding-head algebra, conditionally.** Status: **VERIFIED as working code** (61/61 tests independently reproduced), **PLAUSIBLE as a fit for Cubby specifically**. The four-layer pipeline — `core.py` (bind = elementwise product, bundle = elementwise sum + sign threshold, permute = cyclic shift, all on D=10000 bipolar {-1,+1} int8 vectors), `sdm.py` (Kanerva associative storage), `graph.py` (`SequentialHyperGraph`, chains simple binds for combinatorial reach), `resonator.py` (`ResonatorNetwork`, iterative factorization via continuous-softmax cleanup, RMS renormalization, verified stochastic restarts) — is real, vectorized, honestly documented (it proves and tests a negative capacity result rather than hiding it). F=3 factorization holds 100% accuracy up to codebook size ≈80; F=2 (the plain binding-head case) is trivial to codebook size 1000+. The condition: this only drops in cleanly if CubbyLLM's binding head can operate in bipolar ±1 space and doesn't need to be trainable/differentiable — there are no learned parameters anywhere in this code, `bind`/`bundle`/`permute` are fixed algebra and the resonator's codebooks are pre-generated, not trained. **Validate** by checking whether Cubby's current `VSABindingHead` representations are already bipolar-compatible, or would need a binarization/quantization step (or a low-risk torch port of what are conceptually simple elementwise ops) first.

**Validation result (2026-07-23 campaign): condition RESOLVED — binarization is ~free in the operating regime.** Test suite re-reproduced again (61/61, 55.1s). The head's continuous query keeps cos 0.798 with its sign() (the theoretical √(2/π)), and in the regime that matters (query cos≈0.55 to its target codeword) binarized readout keeps **100.0%** top-1 target retention at D=10240, V=4096. (Zero-signal worst case: 17.6% argmax agreement — reported for honesty; not the operating point.) H-B1's bipolar algebra is compatible with the head via a cheap sign(). `validation/exp_b_algebra.py`.

**H-B2 — GrillCheese's `holographic_relation_test.py` + `brain_resonator_test.py` is a second, independently-useful reference implementation.** Flagged by its own survey as "the single most relevant find for CubbyLLM's VSA/HDC binding-head work." Real, dependency-free (NumPy+FFT), tested, runnable code: Holographic Reduced Representation binding (`bind(a,b) = real(ifft(fft(a)*fft(b)))`, circular convolution — a *different* algebra than cubby-concepts' elementwise bipolar bind), unbind via correlation, a genuine resonator network doing the classic Frady/Kent/Olshausen/Sommer iterative decode loop, plus a binary/bipolar "Vulkan-ready" variant (>95% classification accuracy in testing) closer to Binary Spatter Code. Status: PLAUSIBLE, VERIFIED as real runnable code but not benchmarked at CubbyLLM's scale. **Validate** by comparing HRR/circular-convolution against Binary Spatter Code/elementwise-bind directly against Cubby's actual requirements before choosing — they are genuinely different algebras (HRR handles real-valued/continuous vectors more naturally; BSC is simpler and cheaper in hardware) and the choice has real downstream consequences, not just a naming difference.

**Validation result (2026-07-23 campaign): head-to-head run at D=10240.** Role-filler unbind from bundled superpositions (100-filler codebook): both algebras hold ≥97% recall out to **n=320 bound pairs** — far beyond any realistic binding-head load; first separation only at n=320 (HRR 100%, BSC 97%). Capacity does not decide this choice; representation compatibility does — HRR unbinds the head's continuous query natively, BSC needs the sign() step H-B1's result just showed is ~free. Note H-B5's confirmation adds a third family (grilly's NVSA block codes) whose docstring targets exactly this continuous-vs-bipolar tension. `validation/exp_b_algebra.py`.

**H-B3 — The current binding head's unbind is a structural placeholder, so this is new-build, not patch work.** Status: **re-check DONE (2026-07-23 campaign) — the claim as written was MISATTRIBUTED, the conclusion survives.** `vsa_binding_head.py` was reread in full: it contains **no `UNBIND_ROLE` and no unbind mechanism of any kind** — it is a clean, well-engineered cosine-readout head (continuous query projection → cosine vs fixed bipolar codebook → τ·softmax; the only `UNBIND_ROLE` in cubby-lm is a tokenizer special-token string). The dict-lookup `UNBIND_ROLE` is **cubemind VM code**: `reasoning/vm.py:602-606`, `_unbind_role` returns `self._role_bindings[reg].get(role)` — confirmed never touching `bc.unbind`. So: real unbind must indeed be built from scratch (candidates H-B1/H-B2/H-B5), but it is VM/reasoning-side work, and the LM head is NOT broken — arguably the strongest piece of predecessor code reviewed.

**Re-confirmed unchanged 2026-08-02, with a detail that makes it worse than "placeholder".** `cubemind/reasoning/vm.py` L602-606 is still `return self._role_bindings[register_name].get(role_name)` — a dict lookup. But the *write* side does real algebra and then discards it: `_bind_role` (L575-600) computes `bound = self.bc.bind(role_vec, filler_vec)` and bundles it into the register (L591-593), then at L598-600 shadows the same association into a plain Python dict — **and the dict is the source of truth**. So the VSA is computed and thrown away. All four `tests/test_vm.py` assertions (L462-486) read through the dict, giving the algebra zero test coverage. Real `bc.unbind` exists (`cubemind/ops/block_codes.py` L157, numpy fallback L411) and six other opcodes use it (`_diff` L610, `_detect_pattern` L630, `_recall_position` L770, `_learn_transformation` L813, `_discover_sequence` L839, `MindForge.verify_duality` L283) — so this is one targeted placeholder, not a repo-wide gap. **Nothing to port for the hard part:** grep for `resonator` across cubemind's Python returns a single hit and it is a comment (`vm.py` L75). No resonator, no iterative factorization, no SDM. `CleanupMemory` (`vm.py` L68) is a brute-force linear scan over a dict, and cubemind's own `vm.md` L213 concedes it "needs C++ with grilly's hamming_topk".

**H-B4 — Multi-factor unbinding needs chained F=2 hops, not one large resonator solve.** This is a hard capacity ceiling, not an implementation weakness: flat F=5 factorization is mathematically proven impossible at D=10000 (P_cap ≈ 0.64·D^(1/(F-1))), and cubby-concepts ships a passing regression test (`test_resonator_quadrillion_is_beyond_capacity`) asserting exactly that. Status: VERIFIED (the capacity math and the test both exist and pass). The demonstrated workaround — `vsa/graph.py`'s `SequentialHyperGraph`, chaining simple F=2 binds through an SDM, verified 100% accuracy from depth 1 to depth 20 with zero error accumulation — is how the design reaches combinatorial reach from polynomial storage. **Validate/apply directly:** any CubbyLLM binding-head design that needs more than ~3 simultaneously-bound factors must budget for chained decomposition from the start; this isn't optional future-proofing, it's a known mathematical limit.

**Real-workload datum + a correction (2026-08-02), from cubemind's I-RAVEN crosstalk note (dated 2026-03-19).** This is the first measurement of what bundle load the VM channel actually needs, and it is a task metric rather than a probe: I-RAVEN sits at 86.1% overall, with single-entity configs (Center, L-R, U-D, O-IC) at **96-100%** but multi-entity grids (2x2, 3x3, O-IG) stuck at **67-77%**. The split is capacity — a grid panel bundles 9 object-position pairs into one vector and unbinding SNR falls below the discrimination threshold. Three things follow.

(1) **The note's proposed "expand to k=32, l=256 (d=8192)" should instead be the shape already decided in H-B5: k=80 x l=128 = d=10240.** cubemind runs I-RAVEN at k=16 x l=128 = d=2048, i.e. 5x under the standardized algebra. Moving to the decided shape keeps l=128 (block length unchanged, so codebooks and shaders stay compatible) and only adds blocks, whereas 32x256 invents a third shape and breaks the "one algebra across model + world-arena" property that was the entire point of H-B5.

(2) **The note's "exponentially more capacity" is wrong and should not be planned against.** Bundling crosstalk falls as ~1/sqrt(D) — this project already measured the law in H-C7 (max-crosstalk grows as sqrt(2 ln V / D)). So 2048 -> 8192 is 4x D for **2x** SNR, and 2048 -> 10240 is 5x D for ~2.2x. Real and worth doing, roughly linear in D — not exponential.

(3) **Hierarchical bundling is not a new fix; it is H-B4, and it only works with cleanup between levels.** Bundling objects into rows and then rows into a panel is exactly the chained F=2 decomposition described above, already VERIFIED at 100% accuracy from depth 1 to depth 20 in `cubby-concepts/vsa/graph.py`'s `SequentialHyperGraph`. The critical detail the note omits: that result holds *because* the chain passes through an **SDM cleanup at each hop**, which resets accumulated noise. Without a cleanup step between levels, hierarchical bundling merely redistributes the same total crosstalk across two hops and buys far less than it appears to. Port the SequentialHyperGraph pattern, not just the two-level idea.

Also note the regime: I-RAVEN objects share attribute vocabularies (shape/colour/size), so the fillers are **correlated**, not quasi-orthogonal. H-G2 measured that penalty directly — real keys ran 3.1x more correlated than random bipolar and cost every candidate 2-3x recall. Capacity here is therefore worse than random-vector math predicts, which is consistent with 9 items straining a space where H-B6's probe held ~97% retrieval at n=16 on quasi-orthogonal trunk features.

**A caution carried over from H-B6, aimed at the note's closing claim.** It states that a CNN -> blockSoftmax -> bind/unbind pipeline "can learn hierarchical bundling automatically via backprop" because "the VSA algebra is its own adjoint, so the gradient naturally discovers the right decomposition." The adjoint half is true and elegant: the adjoint of bind-by-b is correlation-by-b, which is unbind. The inference from it is exactly the assumption H-B6 falsified. A differentiable VSA pipeline has a degenerate solution available — collapse the encodings so everything scores well on the objective while losing discrimination — and it will take it: optimizing `binding_aux_loss` alone drove filler-filler cosine 0.006 -> 0.974 and retrieval 96% -> chance, while the loss looked like clean progress the whole way. I-RAVEN accuracy is a real task metric and would eventually catch that, unlike the proxy H-B6 used. But "did hierarchical decomposition actually emerge" needs its own discrimination check; do not infer it from the loss curve.

## 5. Group C — Vocabulary, tokenization, and the softmax bottleneck (a core design requirement, not an optimization)

**Reframed 2026-07-23.** CubbyLLM's vocabulary will be significantly larger than cubby-lm's 32k — explicitly *because* the mechanisms below can remove the full-vocabulary softmax step that would otherwise make a large vocab expensive to train and serve. Everything in this group graduates from "worth checking if it helps" to "the output-head mechanism CubbyLLM's vocab strategy actually depends on." The open question is no longer whether to pursue this, it's which specific mechanism, and how large "much larger" ends up being — both still genuinely open (see H-C6).

**H-C1 — Dynamic hyper-encoder embeddings are the enabling mechanism for a much larger vocabulary, not an optional parameter-count optimization.** Source: ZeTT (hypernetwork predicts token embeddings for any target vocabulary on the fly) and zip2zip, motivated by the observation that static embedding/unembedding tables scale linearly with vocab size and can reach up to 93% of total model params in typical LLMs at 100k+ vocab — the exact regime CubbyLLM is now explicitly targeting, unlike cubby-lm's comparatively modest 32k. Status: SPECULATIVE mechanism (ZeTT/zip2zip are external research, not yet reproduced against CubbyLLM's actual target scale), but no longer optional to check — it's close to a load-bearing assumption behind the vocab requirement itself. **Validate** by prototyping a hyper-encoder generating embeddings on the fly for a synthetic vocabulary at the target order of magnitude, and confirming (a) generated-embedding quality is competitive with a static lookup table at a small/medium vocab size where both are still cheap enough to compare directly, and (b) the hyper-encoder's own compute cost per token doesn't reintroduce the cost problem the static table was supposed to avoid. **Kill criterion:** generated embeddings measurably underperform static ones at matched vocab size, or the hyper-encoder's forward cost scales badly enough to erode the "fast" half of the goal — either result means the large-vocab requirement needs a different enabling mechanism, or a smaller target vocab after all.

**Validation result (2026-07-23 campaign): kill criterion HALF-triggered at toy scale.** On the real spm32k token stream (cubby-lm valid.txt, V=8k kept, d=64, identical budgets): the **quality clause FAILS** for a pure surface-form generator — static table val loss 3.886 (ppl 48.7) vs char-CNN hyper-encoder 4.389 (ppl 80.6), +0.50 nats; surface form alone cannot recover what a table memorizes. The **cost clause PASSES decisively** — 1.26µs/token to regenerate the full table, cacheable at inference, embedding params V-independent (77k vs 578k). Read alongside zip2zip's actual design (static base vocab + composed hypertokens), this steers toward a **hybrid** (static core + generated/composed tail), not pure generation — see H-C6. Toy-scale caveat stated in the log; re-check at target scale before betting the vocab strategy. `validation/exp_c1_hyperencoder.py`.

**H-C2 — zip2zip-style LZW hypertoken compression reduces autoregressive step count 20–60%, directly improving latency.** Status: **VERIFIED (2026-07-23 campaign — measured on the real tokenizer, no model change).** grillcheese_spm32k_v2 over 8MB of cubby-lm's valid.txt (2.07M base tokens): **per-document (streaming-honest) reduction 22.2%** — the claimed range reproduced at its low end; a *persistent cross-document dictionary* reaches **53.4%–66.6%** (32k→992k hypertokens minted) — at/above the claimed top. **H-C3 — Removing the full-vocabulary softmax is the specific mechanism that makes a much larger vocabulary affordable at the output head.** The general pattern (retrieve top-K via an ANN index, softmax only over those, instead of a full-vocabulary softmax) is exactly what cubby-lm's `VSABindingHead` cosine-similarity-against-a-frozen-D=10240-codebook already did structurally, so it's not a foreign idea to graft on — it's an extension of something the predecessor already had the right shape for. GrillCheese's `gcheese-faiss/` module is a small-scale (sub-100k item) working existence proof this pattern is production-viable: a hand-written Vulkan GPU reimplementation of brute-force kNN (built because CUDA faiss-gpu doesn't run on their AMD hardware), running *side by side* with a separate softmax-attention memory-read path that they are actively optimizing — i.e., a real system where both approaches coexist and get compared. Status: PLAUSIBLE, and the clearest "this is already almost what we do" finding in the whole survey. Self-reported performance figures (sub-2ms @ 10k memories, 2-5x GPU speedup) are explicitly flagged by their own `CRITICAL_ISSUES.md` as unvalidated planning targets, not measurements. **This is no longer a formalize-what-already-exists nice-to-have — it's the specific mechanism the new, larger vocabulary is being designed around, so it needs validating at the target vocab scale, not at cubby-lm's old 32k.** **Validate** by building an explicit ANN-retrieval output head (or a Sylph-style sigmoid-decomposed alternative, per H0) at a representative large-vocab scale and benchmarking latency/accuracy against a full-softmax baseline at the same scale, not against cubby-lm's existing numbers.

**Validation result (2026-07-23 campaign): mechanism confirmed REQUIRED; bounds measured (CPU, batch=1).** Full-head cost is linear in V (measured 7.8× for 8× vocab at d=2560; 47.9ms/token at the real 32k×10240 shape). The retrieval floor (exact scoring over a K=1024 shortlist) is ~flat at 0.2–1.5ms — a **32× win at the real head shape**. Naive IVF over *random* codewords is the pessimistic bound and it's poor (37–80% top-1 agreement, falling with V) — index quality on *trained* embeddings is the real engineering question before committing to a specific ANN. The decisive number is memory: **V=1M fp32 codebook = 10–41GB** (d=2560/10240; the 1M row is explicit linear extrapolation, not measurement) — at large V the softmax bypass isn't an optimization, it's the only way the head exists. **H-C6 — CubbyLLM's vocabulary may not need to be a fixed-size discrete set at all.** Added 2026-07-23. zip2zip's inference-time LZW hypertoken compression and ZeTT's target-vocabulary-agnostic embedding generation both point toward an open-ended vocabulary — new hypertokens formed and embedded on demand, no fixed upper bound chosen in advance — rather than simply picking a bigger fixed number than 32k. Status: SPECULATIVE, and genuinely undecided: "much larger" could mean a large-but-fixed vocabulary (say 250k–1M, sized once, a more conservative extension of what cubby-lm already did) or an effectively open/dynamic one (no fixed size, tokens/hypertokens minted at inference time, closer to zip2zip's actual proposal). **DECIDED (user, 2026-07-23): HYBRID.** Fixed core vocabulary — next step a 128k–256k BPE on the proven H-G1 pipeline — plus a retrieval output head from day one, with the hypertoken/dynamic tail deferred as a later, separately-gated addition. **H-C7 — A much larger vocabulary strains the VSA binding head's codebook capacity and needs its own sizing pass.** Added 2026-07-23, a direct consequence of combining H-B4's capacity law with this group's new vocab requirement. Status: SPECULATIVE — this hasn't been worked through as its own design question yet, it's a mathematical consequence of two already-gathered pieces of research meeting for the first time in this revision. **Validate** by computing the actual required D for the target vocabulary size once one is chosen (H-C6), against the same capacity formula already verified in cubby-concepts' test suite, before assuming cubby-lm's D=10240 sizing transfers to a much larger vocab.

**Validation result (2026-07-23 campaign): RESOLVED with numbers — the fear was aimed at the wrong place.** **Direct one-codeword-per-token readout does NOT strain at D=10240**: max-crosstalk grows only as √(2lnV/D), leaving a +0.50 cosine margin for a cos=0.55-quality query even at V=1M (empirically 100% top-1 at every V tested up to 1M). What DOES break is **flat factored identity**: per-slot resonator capacity at D=10240 is F=3: 65, F=4: 14 (verified law), so V=1M at F=3 needs 100/slot (over capacity) and F≥4 is hopeless; single-token factored readout at 1M would need D≥24k (F=3) or D≥121k (F=4). Chained F=2 hops (H-B4) remain the escape hatch if factored identities are ever wanted. The real large-vocab pressure is the flat codebook's memory + O(V·D) compute — i.e., H-C3's problem, not binding-algebra capacity. `validation/exp_c7_capacity.py`.

## 6. Group D — Backbone architecture hypotheses

This group comes from a single "trillion-parameter architecture blueprint" document the user supplied "to validate and see how it fits." It bundles dynamic tokenization (already covered in Group C), a BDH+TTT backbone, a GCE controller (already the central bet, H0), and AIMC hardware (Group E) into one end-to-end pitch, plus a multiplicative energy-savings calculation. It should not be adopted as a package — each piece is at a different maturity level, and the blueprint itself is a synthesis document, not an implementation.

**H-D1 — BDH's Q=K constrained attention-free recurrence is a candidate backbone for CubbyLLM, one option among others including cubby-lm's MinGRU approach.** Status: PLAUSIBLE — BDH and its `bdh-cl` continual-learning extension are real published architecture work, but the efficiency numbers attached to them (35x faster training, 10x lower inference) come from CIFAR-10/Sudoku-scale experiments, not LLM-scale text modeling. Since CubbyLLM's backbone is being chosen fresh rather than inherited, this is a genuine head-to-head decision, not a replace-in-place question. **Validate** at small scale on a real token-modeling task before assuming these numbers transfer — image/puzzle-benchmark speedups are not evidence about a multi-billion-parameter text model.

**Validation result (2026-07-23 campaign): VIABILITY checked, real decision still deferred.** Matched-size char-LM bake-off (`validation/exp_d1_backbone.py`, d=128/L=4/2500 steps, real valid.txt, cubby-lm's ACTUAL MinGRULayer imported): an attention-free Q=K recurrence learns text competitively (1.584 bpc, far ahead of small softmax attention's 2.470) at lower per-step latency — but **MinGRU is the best learner here** (1.454 bpc, +0.13 over the Q=K mixer).

**RESOLVED (2026-07-23): the in-architecture bake-off picked MinGRU.** `validation/exp_d1b_backbone_bakeoff.py` plugged four candidates into the *real* assembled `CubbyModel` (frozen router → hybrid embedding → backbone → hardened memory → learnable head) on the real subword-TinyStories setup, matched budget, every non-backbone component built from the same per-component seed so the backbone was the only variable. Held-out perplexity / bpc: **gru 34.0 / 1.300, mingru 34.8 / 1.308, bdh(Q=K) 49.1 / 1.435, attn 48.0 / 1.427.** Two clean clusters: gated recurrence (GRU, MinGRU) beats the attention-free Q=K recurrence and softmax attention by ~10% bpc at this scale. GRU vs MinGRU is within single-run noise, but MinGRU matches GRU's quality at **25% fewer backbone params**, with the log-domain parallel scan (throughput at scale, where GRU's kernel is sequential) and continuity with cubby-lm. **User decision: MinGRU is the package default backbone** (`cubbyllm/model/backbone/mingru.py`, `MinGRUBackbone` — a RMSNorm + MinGRU-recurrence + SwiGLU trunk; the interface-only `base.py` keeps alternates pluggable). The 35×/10× BDH efficiency claims remain untested (need scale + a faithful BDH impl); at this scale BDH-Q=K is a viable-but-not-winning contender.

**H-D4 — the H-D1 bake-off chose the backbone on bpc, which is blind to content-based retrieval; a windowed-attention hybrid beats pure MinGRU on long-context recall, at bounded state.** Status: **scale-VERIFIED (2026-08-04) — decisively.** *(Renumbered from a duplicate H-D3; the energy-claim H-D3 below predates this entry.)* The H-D1 bake-off scored on held-out **bpc** — a next-token-prediction metric. Attention's mechanistic edge is *content-based lookup* ("where did this token appear before, and what followed it"), the induction-head circuit, which barely shows up in average perplexity and is exactly what a long-document/needle capability needs. So H-D1 resolved the backbone on the one axis that cannot see the thing at issue. The dense-induction probe (`validation/exp_d3_induction.py`, canonical repeated-sequence task, per-position loss on the second half, d=128/L=6, multi-seed) measures it directly. Result, sweeping distance across the window (`window=96`): at **T=64 (within window)** pure MinGRU **0%**, full-attention hybrid **100%**, windowed hybrid **100%** — bounded state; at **T=256 (beyond window)** MinGRU **0%**, windowed hybrid **0%** (collapses to MinGRU, as it must — a 96-token window cannot reach 256 back), full-attention hybrid still **100%** (unbounded). So the windowed arm buys distance-robust recall out to ~window (×depth for stacked layers) at *fixed, context-independent* state, and no further; full attention solves at any distance but only by paying a KV cache that grows with context. The mechanism is controlled, not inferred (verified: within-window 100% by step 100; beyond-window `W=16,T=32` stuck at chance). This is cubby-lm's own production shape (attention every 3rd layer, 8 of 22, `trunk_torch/blocks.py`), which CubbyLLM had dropped without a decision. **Why windowed, not full:** full attention keeps a KV cache that grows with context, breaking the O(1)-decode guarantee (`tests/model/test_mingru_decode.py::test_state_size_is_independent_of_context_length`) that the inference-cost thesis rests on; a sliding window keeps per-attention-layer state at O(window) = constant. **Built:** `cubbyllm/model/backbone/hybrid.py::HybridBackbone` (MinGRU + windowed attention every Nth, **RoPE** on the attention so it is position-aware — the package has no other positional signal and MinGRU-implicit position would leave layer-0 attention blind; RoPE also extrapolates train-S to the 4096 needle length; bounded-KV `step()` that reproduces `forward()` even across window slides), `__wiring__ = STANDALONE` (pluggable alternate, **not** the default), drops into `CubbyModel` with no assembly change; `tests/model/backbone/test_hybrid.py` (8) pins decode-equivalence, bounded state, window reach + the ~depth×window compounding of stacked windows, and RoPE position-awareness. Wired through `train_colab.py` (`CB_BACKBONE=hybrid`, meta-recorded) and `exp_needle_recall`/`exp_decode_throughput` (reconstruct backbone from meta) so the A/B is a single flag. **Kill criterion / open:** (1) toy-scale only — re-run at the 413M shape on real **needle recall across lengths**, pure-MinGRU vs windowed-hybrid, before making the hybrid the default; (2) the honest limit for the 1M-context pitch — *no* bounded-state model does arbitrary-distance recall; windowed attention extends distance-robust recall to ~depth×window tokens at fixed state, and beyond that recall falls back to what the recurrent state retains. `validation/exp_d3_induction.py`, `validation/logs/exp_d3_*`.

**Scale result (2026-08-04): DECISIVE — kill-criterion (1) retired.** Two matched runs, identical except `CB_BACKBONE` — pure MinGRU vs windowed-hybrid (MinGRU + windowed attention every 3rd of 8 layers, `window=512`, RoPE), d=512 / L=8 / ~0.98B tokens each — scored on `exp_needle_recall` (PMI, shuffled + untrained controls, argmax-spread check) across lengths **256 / 512 / 1024 / 4096**. Floor: MinGRU's shuffled control ~15%, untrained ~33% (a PMI base-rate residual), chance 12.5%. **Pure MinGRU (trained): ~28–32% at every length** — barely above its own shuffled floor, flat, weak. **Windowed hybrid (trained): ~98% at 256, ~100% at 512** (every depth except the window-edge depth 0.0 = 41.7%), and at **1024 the depth pattern IS the window, drawn to a single step:** `16.7 / 16.7 / 8.3 / 91.7 / 100` — chance while the needle sits beyond the 512 window (depths 0.0–0.5), near-perfect once it is inside it (depths 0.75–1.0), the transition landing exactly at the window boundary. Recall is a pure function of one variable — **needle-to-query distance vs window**: inside → ~100%, outside → chance. That fingerprint rules out memorisation or artifact; it is the sliding-window mechanism itself, at scale. So a windowed-attention hybrid gives near-perfect long-context recall within its window at bounded, context-independent state, and pure recurrence does not (**98% vs 32%** at 256). The honest bound is in the same data: beyond the window the hybrid falls to the floor like MinGRU — windowed attention buys perfect recall to ~window (×depth for stacked layers), no further; recall *past* the window is the memory layer's job (rung 0.0.5, still unbuilt). **Decision: the backbone is the hybrid** — H-D1's "RESOLVED: MinGRU" is superseded; it was resolved on the one metric (bpc) that cannot see retrieval. `validation/logs/needle_mingru.log`, `validation/logs/needle_hybrid.log`.

**H-D2 — In-place Test-Time Training eliminates the KV-cache but is a compute-for-memory trade, not a free win.** The blueprint proposes repurposing FFN projection layers as dynamically-updated fast weights during inference, updated via local next-token-prediction gradients, to handle long context (128k tokens) without KV-cache memory-bandwidth cost. Status: SPECULATIVE as a net win — TTT's per-token update is itself a gradient step, so inference compute per token goes up even as cache memory goes down. **Validate** by measuring wall-clock/FLOPs per generated token with TTT-in-the-loop versus standard KV-cache attention at matched context length — the blueprint only argues the memory side, not the compute side, of this trade.

**Validation result (2026-07-23 campaign): compute side now measured (d=512, CPU, rank-1/NLMS-style update — the cheap TTT variant).** TTT per-token cost is constant 0.253ms; KV-attention grows 0.545→210.4ms from L=1k→131k; measured crossover **L≈1,024 (≈d)** — so on this shape the compute side *also* favors TTT for essentially all long-context regimes, rather than opposing the memory win (1.0MB vs 536.9MB state at 128k). Two honest limits: full-backprop TTT variants cost more than the rank-1 form measured, and — stated plainly — nothing here tests whether local-gradient fast weights actually *retain* 128k tokens of usable context. The quality half still needs a trained model. `validation/exp_d2_ttt.py`.

**H-D3 — HIGH SCRUTINY: the blueprint's ~2,250x (reduced to "~1,900x" after a 15% overhead haircut) total energy-reduction claim should not be treated as a real number.** It's constructed by multiplying four independently-sourced factors: ~90x from eliminating weight-loading via analog in-memory compute, 2.5x from zip2zip-style sequence compaction, 5x from spike-based activation sparsity, 2x from softmax/KV-cache bypass. Status: SPECULATIVE, and specifically flagged here because multiplying independently-sourced efficiency claims from four different papers/contexts is not evidence they compose in one real system — savings mechanisms frequently target overlapping bottlenecks (if weight-loading is already ~90x cheaper via analog compute, the marginal value of also cutting softmax cost is not obviously still a clean independent 2x on top), and none of these four numbers were measured together in a single working pipeline anywhere in the source material. **Validate only by building an integrated small-scale prototype and measuring the composed number directly.** Treat 1,900–2,250x as a theoretical ceiling under best-case independence assumptions, never as a planning number.

BinaryOps/HolographicOps remain reference implementations, not the standard. **Two grilly hazards found while surveying it for reusable VSA work (2026-08-02).**

(a) **`blockcode_bind` exists twice with different semantics, and one silently corrupts bundles.** `grilly.experimental.vsa.block_ops.BlockCodeOps.bind` (what `cubbyllm.ops.BlockCodeVSA` actually calls) is true per-block circular convolution. `grilly.backend._bridge.blockcode_bind` — both the GPU shader `shaders/blockcode-bind.glsl` and its numpy fallback — is a one-hot **argmax shift**: it scans `if (a[i] > 0.5) hot_a = i`, so on a continuous block code (every entry < 0.5, since each block sums to 1 across l slots) both indices stay 0 and it returns the **identity element without raising**. CubbyLLM is safe only because its ops seam never dispatches to `_bridge` — see the TODO item, which now says *do not* wire that dispatch. grilly's own `tests/test_blockcode.py` cannot catch this because every test uses strictly one-hot inputs; there is no test anywhere in grilly that unbinds from a superposition. Ours now has three: `tests/ops/test_vsa.py`.

(b) **`blockCodeCodebook` caps at n <= l — 128 codes at l=128.** IBM's successive-binding construction walks the cyclic group Z_l per block with the same shift each step, so it wraps after exactly l entries; the C++ raises `n must be <= l`, and the Python twin *silently* degrades to random sampling "(may have collisions for large n)". Irrelevant for role/filler duty (n=16), but it means the decided k=80 x l=128 shape cannot supply a large concept codebook by that construction. Independent random one-hot per block gives ~l^k distinct codes with birthday-bounded collisions, at the cost of algebraic closure — budget that design choice before the VM needs a vocabulary-scale codebook.
