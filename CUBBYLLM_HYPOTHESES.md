Nothing here is a commitment to build anything — it's the accumulated research and concept-survey material from the CubbyLLM planning phase, organized so each claim can be checked before engineering time gets spent on it.

## 0. How to use this document

Every hypothesis below follows the same shape: a claim, why we currently believe it (which source it traces back to), a concrete way to check it, and what result would kill it. A hypothesis with no kill criterion isn't really a hypothesis — it's an opinion — so every entry has one even where it's approximate. Status is one of **VERIFIED** (independently reproduced this session, not just asserted by a source document), **PLAUSIBLE** (a real source claims it, mechanism makes sense, but nobody has measured it against Cubby's actual code), or **SPECULATIVE** (asserted in a vision/blueprint document with no implementation behind it at all).

Hypotheses are grouped by the two structural problems driving the redesign (memory/forgetting, VSA binding head), then by the two halves of the one-line goal (fast/profitable, automatic specialization), then backbone and hardware, then a small set of organizational hypotheses, then training-data findings. Section 10 gives a suggested validation order — cheapest and most falsifiable first, hardware last.

## 1. Context

**Goal (one-liner):** Fast and profitable LLM gen 2 hybrid — general tasks plus specialization, automatic.

CubbyLLM is the redesigned successor to `cubby-lm`, drawing on lessons from `cubby-lm` and its environment sibling `cubemind`. Two concrete problems motivate the redesign, both already scoped by the user:

**Problem 1 — VSA binding head.** Cubby's current `VSABindingHead` operates over a frozen D=10240 codebook. **Corrected 2026-07-23 (validation campaign):** the dict-lookup `UNBIND_ROLE` this paragraph previously attributed to the binding head actually lives in **cubemind's VM** (`reasoning/vm.py:602-606`) — `vsa_binding_head.py` contains no unbind mechanism at all; it is a clean cosine-readout output head. The real-unbind gap is real but sits on the VM/reasoning side; the binding-head work for CubbyLLM is a from-scratch build either way (see H-B3, H-B5).

**Problem 2 — Hebbian memory layer.** The current Hebbian/Oja-style memory update is detrimental to memory: it drifts and forgets catastrophically under sequential learning. This needs fixing using the research summarized in Section 3.

**Structure — two different axes, kept deliberately separate.** CubbyLLM's *package/directory layout* will likely mirror cubemind's — meaning cubemind's intended, documented structure, not its accumulated sprawl (see Group F). CubbyLLM's *model architecture* is a different question entirely: **CubbyLLM is an entirely different structure than cubby-lm, built from scratch, including the vocabulary** (correction, 2026-07-23). cubby-lm's trunk is prior art — informative about what worked, what didn't, and what to avoid repeating — not a frozen substrate CubbyLLM has to sit on top of. Nothing below should be read as "patch cubby-lm's trunk"; where a hypothesis references cubby-lm's actual code, it's diagnosing the predecessor to inform a fresh design, not scoping an in-place edit.

**New, explicit requirement (2026-07-23): a much larger vocabulary than cubby-lm's 32k, unlocked specifically by removing the full-vocabulary softmax step.** The causal order matters and is worth stating precisely: vocab size is being treated as a variable that gets freed up once the output/embedding mechanism stops paying an O(vocab) cost per step — not a number chosen first that then needs optimizing around. This promotes what was previously framed as a set of possible efficiency optimizations (old Group C) into a load-bearing design requirement; see the rewritten Group C below, including two new hypotheses (H-C6, H-C7) this requirement surfaces.

cubby-lm's own shape, kept here for reference and lessons-learned, not as a CubbyLLM constraint: d_model=2560, n_layers=22, d_ffn=6848, tokenizer `grillcheese_spm32k_v2` (32k SPM, frozen in cubby-lm), MinGRU recurrence per `HybridBlock` with optional MoE / sliding-window attention / `EpisodicMemory` / SwiGLU FFN. `SegmentMemory`, `MTP`, and `CubeLangHead` exist as code but are not wired into the default forward pass — `CubeLangHead` is self-labeled "SCAFFOLD." Worth carrying forward deliberately rather than repeating by accident: the value of gating each new capability behind an explicit version flag, and the risk of building attachments (MTP, CubeLangHead, SegmentMemory) that never get wired into the actual forward path.

**Training data (added 2026-07-23):** a real, substantial corpus (~210GB) exists at `D:\grillcheese_training_data` — the user's own framing was that it can be used both for testing and as raw material for "a better dataset." Full findings are in the new Group G below, but the single most consequential discovery deserves a mention here: a training-data-generation script in this folder revealed an already-existing, already-in-production VSA/hyperdimensional-computing implementation (`grilly.experimental.vsa.ops`) running at the exact same D=10,240 dimensionality as both cubby-lm's binding head and cubemind's world-arena block-codes. That's not yet confirmed to be the same substrate, but it's a strong enough lead that it now sits at the top of Group B's validation order (H-B5), ahead of the two candidates the earlier survey found.

## 2. The central bet (H0)

**Claim.** Context-conditioned, hypernetwork-style parameter generation — making a model's active weights a function of context, θ=f(c), rather than a fixed state that gets overwritten in place — is simultaneously the fix for catastrophic forgetting *and* the mechanism for automatic specialization. If true, the two halves of CubbyLLM's one-line goal ("general tasks" and "specialization automatic") collapse into one underlying mechanism rather than two separate subsystems.

**Why we believe it.** Three independent sources converge on this same shape, which is a stronger signal than any one of them alone:

The Gradient Context Encoder (GCE) work (Ran Cheng, "Context Channel Capacity") argues catastrophic forgetting is mathematically forced whenever a state-based learner runs at C_ctx=0 — i.e., whenever weight updates don't structurally depend on context — and that the fix is making θ an unbypassable function of context, f_GCE(c), verified by Wrong-Context Probing (P5) so the context signal can't be optimized away in training (the "Structural Bypass Defect"). This closed a CIFAR-10 oracle gap from 23.3pp to 0.7pp in the source material.

Sylph, independently, replaces global softmax classifiers with sigmoid-decomposed binary classifiers whose parameters are generated by a few-shot hypernetwork conditioned on task embeddings — explicitly to avoid global gradient interference and prevent forgetting during sequential task adaptation. Same shape (hypernetwork generates params from context), different framing (classifier heads, not general weight rectification).

Dragon Hatchling (BDH) arrives at a related idea from the architecture side: its `bdh-cl` continual-learning extension pairs fast local Hebbian plasticity with mechanisms to keep it from drifting, and the broader "trillion-parameter blueprint" research (Section 6) explicitly proposes a GCE-style controller as the piece that prevents BDH's in-place Test-Time-Training fast weights from drifting.

**What's notable:** none of the four surveyed sibling folders (cubby-concepts, AURA_GENESIS, GrillCheese, Novel_GNN_Arch) implement this pattern anywhere. The closest analog is AURA_GENESIS's Liquid-MoE `tau(x)`-conditioned continuous-time gating cell (`aura/core/liquid_moe.py` — real, working, NumPy-only), which is *routing* (selecting among fixed experts) rather than *generating* continuous parameters, but is a plausible template for the small controller network that would emit the context embedding driving a hypernetwork. This means H0 is genuinely new work for CubbyLLM, not something to import — everything downstream in Groups A–D is really this one bet applied to different parts of the model.

**A fourth independent instance, added 2026-07-23:** generating token embeddings from context instead of storing them in a static lookup table (Group C's H-C1/H-C3, now driven by the much-larger-vocabulary requirement in Section 1) is itself a specific case of H0's mechanism — θ_embedding = f(token/context) rather than a fixed embedding matrix. The vocab requirement and the forgetting fix aren't two unrelated bets that happen to share a document; they're two applications of the same underlying idea, this time one driven by a hard product requirement rather than a research paper. That's a reason for more confidence in H0, not less.

**How to validate.** Build the smallest possible GCE-style controller (a context embedding feeding a rectification to one small weight block, not the frozen trunk) and run the P5 Wrong-Context Probing protocol against it, plus a toy sequential-task retention benchmark, compared against a frozen-weight baseline and the current Hebbian layer.

**Kill criterion.** If P5 probing shows the context signal gets optimized away even after architectural hardening (the Structural Bypass Defect resists the standard countermeasures), or if the added hypernetwork forward/backward pass erases the "fast" half of the goal at the scale CubbyLLM actually needs, the central bet needs revision — not abandonment, but a scaled-down or partial version (e.g., gating only specific memory slots rather than general weight generation).

**Validation result (2026-07-23 campaign): SUPPORTED at toy scale, with one load-bearing caveat.** The smallest θ=f(c) prototype (frozen backbone per this section's own protocol, hypernetwork-generated head, 6 sequential tasks, no replay) shows near-zero forgetting **only with architectural hardening** (von-Oswald-style output regularization — literally the hypernetwork output regularizer of von Oswald, Henning, Sacramento & Grewe, *Continual learning with hypernetworks*, ICLR 2020, arXiv:1906.00695; citation pinned here 2026-08-28 after the oracle-competition scoring in `docs/research/2026-08-28-oracle-competition-scored.md` noticed it lived only in the agenda's Q6 note): task-0 MSE 0.062→0.060 across all tasks, P5 right-ctx 0.06 vs wrong-ctx 1.87 (context load-bearing, no bypass). The **naive** hypernetwork without hardening ends *worse than the fixed-weight baseline* (2.734 vs 1.778 final MSE) — the hypernetwork's own shared weights are themselves a C_ctx=0 learner and interfere internally, and its P5 probe flags bypass. So H0 is only ever "generation + anti-drift countermeasure," never naive generation. Cost: 4.1× baseline per step at toy scale, growing with number of protected contexts — the "fast"-half kill clause stays open at scale. `VALIDATION_REPORT.md` / `validation/exp_h0_gce.py`.



**Stand-in pointer (2026-09-03, `standin/README.md` § "Two adapters on one base — v8"; a `[stand-in]` fact, not a trunk result).** One fine-tuned 2.6B carrying both the program-emission and the talk data was measured to interfere across rounds (identity fell in v5, forge decision 1.00 → 0.17 in v6, arithmetic 0.825 → 0.750 → 0.675 over v5–v7 as the chat volume grew; each repaired by replaying the hurt family ×3/×4). The serve stack now speaks the θ=f(c) interface — `Emitter.emit(…, context=)` with the route role and the hormonal state as c — and resolves it through a K=2 tag-indexed adapter bank (`ContextualEmitter`, the frozen-router shape of H-C4). The v8 A/B (program-only vs talk-only adapters, same base, same 40/task VM eval) is the cheapest measurement of whether context-selected parameters remove that interference; its kill line is recorded there. It says nothing about the trunk's hypernetwork itself.

**A WORKING theta=f(c) IMPLEMENTATION ALREADY EXISTS — found 2026-08-02 in cubemind, port it rather than rebuild.** `cubemind/execution/mindforge.py` (452 lines) is real, runs, and has full analytic gradients: `MindForge.forge(context, layer_id) -> (A, B)` at L302, `forge_with_cache` L309, `backward(d_A, d_B, layer_id, cache)` L358. Its parameterization is the one CubbyLLM should adopt: a block-code hypervector context is projected `W_proj (d_hidden, k*l)`, LayerNormed, concatenated with a per-layer embedding `layer_embeddings (n_layers, d_hidden)`, pushed through an MLP to `W_coeff (n_basis, d_hidden)`, and the generated adapter is a **linear combination of learned low-rank bases**: `A = sum_i coeffs[i]*A_basis[i]`, `B = sum_i coeffs[i]*B_basis[i]`. Verified by execution — gradients populate all 10 parameters, and it is genuinely conditioned on both inputs (layer sensitivity |A(ctx,L0)-A(ctx,L1)| = 2.30; context sensitivity |A(c0,L0)-A(c1,L0)| = 67.15). It is correctly wired into `cubemind/training/vsa_lm.py::VSALayer` (L877 forge, L921 the analytic backward). **This matters because CubbyLLM's own `HyperGenerator` generates a full d*d matrix (ctx_dim=32 -> 4.19M outputs, ~134M params) which will not scale**; the basis-coefficient form is roughly 40x smaller and generates *per-layer* adapters. Two caveats: the GPU path is dead (`_mindforge_gpu_ok()` checks for `mindforge_basis_mix`/`mindforge_bwd_coeff`/`mindforge_bwd_basis` in grilly_core, which do not exist, so everything runs numpy `tensordot`), and there is a stale duplicate `mindforge.patch.py` encoding a removed-softmax design that `harrier_pretrain.py` was written against — that trainer hand-rolls approximate gradients, never calls `forge.backward()`, and has produced no checkpoint. Take `mindforge.py`, not either of those.

**The torch port that exists is DEGENERATE — this is the live gap between the bet and the code.** `cubemind/model/cubby/heads.py::MindForgeLoRAHead` (L17) claims to be a "PyTorch port of cubemind.execution.mindforge" but drops the two things that make it theta=f(c): there is **no layer embedding** (it is per-head, not per-layer) and **no VSA input** (context is a plain dense vector). Worse, it is self-conditioned in every call site — `MinGRUMultiTask.forward` L272 calls `head(pooled)` with `context=None`, and L86-87 then assigns `context = x`, with the default head spec declaring `"task_code_source": "self"`. So in practice it computes **theta = f(h)**, conditioned on the model's own pooled hidden state; no external task/context signal crosses into it at all. The `context=` argument is plumbed and nothing supplies it. Also `basis_B` is zero-initialised there (L80) while the numpy version uses small-random (L243) with the explicit comment "Zero init kills gradients through the LoRA path" — the two implementations contradict each other on their own core design point, so the torch LoRA path may not be training.

## 3. Group A — Memory & forgetting fix

**H-A1 — Diagnosis: the Hebbian layer fails because it runs at C_ctx≈0.** The Impossibility Triangle (zero forgetting + online learning + finite parameters can't all hold for a state-based learner) predicts this. Status: **VERIFIED (2026-07-23 campaign, both halves)** — structurally, the real `HebbianGrowthLayer` update is dW = f(x, xWᵀ, W) with no context input existing anywhere in its signature or update path, so C_ctx = 0 *by construction* (no estimation needed); empirically, after learning a task to EV 0.97 the shared basis retains EV 0.06 (**forgot 94%**) after three subsequent tasks; neurogenesis mitigates to 72% forgotten but doesn't rescue. Two incidental findings: the layer's default `nonlinear` (y³) mode never tracks subspace structure under a reconstruction metric (only `sanger` mode learns), and its residual metric becomes unreliable (EV>1) once grown bases decorrelate. See `VALIDATION_REPORT.md` / `validation/exp_a1_drift.py`.

**H-A2 — GCE-style generation removes catastrophic forgetting in CubbyLLM's memory layer.** Status: **toy-scale VERIFIED in the hardened form** (2026-07-23 campaign — see H0's validation result above for the numbers; the toy experiment *is* this hypothesis's specified side-experiment). Kill criterion checked and not triggered: bypass did not survive hardening. Still open at scale: the hardening cost curve and whether the mechanism stays scoped to the memory pathway in a real model — the second kill clause is untested until there is a real network to scope it in. `validation/exp_h0_gce.py`.

**H-A3 — A Sparse Distributed Memory substrate is more forgetting-resistant than dense Hebbian updates, purely by construction.** Source: `cubby-concepts/vsa/sdm.py` — real code, independently verified this session (staged the files, ran `pytest` directly: 61/61 tests passed, 81.6s wall time). Verified recall: 100% accuracy (1000/1000, cosine similarity 0.9957) at M=D=10000 with 1000 stored associations. Each write spreads across roughly 40 of 10,000 hard locations (calibrated Hamming radius) instead of overwriting one dense weight matrix — the standard SDM graceful-degradation argument versus Hopfield-style catastrophic collapse. Status: **the mechanism is VERIFIED; the forgetting-resistance property itself is PLAUSIBLE, not proven** — the cubby-concepts repo has no test that pushes the SDM toward/past capacity or compares its degradation curve against a Hebbian baseline. The repo's own CLAUDE.md names a "Zero-Forgetting Stability Benchmark" but it doesn't exist as code anywhere — file, function, or test. Also note: the repo proves the CLAUDE.md-specified Hamming radius of 4500 bits is actually broken (activates ~0 locations at full dimension) and ships a regression test for that fixed bug — a good sign for the code's honesty, a reminder to use the calibrated radius, not the originally-specified one. **Validate** by building that benchmark (it doesn't exist yet) and running it against SDM and the current Hebbian layer side by side.

**Validation result (2026-07-23 campaign): the benchmark now exists (`validation/exp_a_forgetting.py`) and the answer is split.** At matched state (~D² numbers each, D=2048, SDM M=D, online single-pass): SDM is the **only order-agnostic candidate** — at N=1024 its recall is ~15% uniformly across write order, while every dense method is recency-biased or totally collapsed (pure Hebbian: 0% for old AND new — overload destroys everything). That's the "graceful by construction" half, CONFIRMED. The capacity half is REFUTED at parameter parity: SDM's curve (99%→77%→15% at N=128/512/1024) sits below NLMS (100%→100%→51%) — the famous 100%@1000 cubby-concepts result used M=D=10000, ~5× the state per stored pair. SDM buys *fairness*, not *capacity*. Status: mechanism VERIFIED, blanket forgetting-resistance claim now has honest boundaries.

**H-A4 — NLMS is a cheaper drop-in replacement than a full hypernetwork rewrite.** Source: `AURA_GENESIS/aura/core/nlms.py` — real, complete, ~14KB, textbook Normalized LMS (`w ← (1−l2)·w + mu·(e·x)/(‖x‖²+ε)`), extended with group-sliced per-feature learning rates, a prosody-style gate, and dead-zone guards that skip updates when the prediction is already close enough. NLMS is error-corrective and self-normalizing by input energy, which classical adaptive-filter theory uses to bound weight drift — a real structural advantage over raw Hebbian/Oja. Status: PLAUSIBLE, with an important caveat surfaced by the AURA_GENESIS survey: AURA's actual anti-forgetting strategy is not "a smarter shared update rule," it's hard parameter isolation — one private linear head per domain/realm (88 domain files + ~150 realm files under `svc_nlms_weights/`), created on demand and never shared across concepts. That sidesteps interference by construction, not through NLMS's math, and doesn't obviously transfer to a shared dense memory layer where isolation isn't an option. **Validate** by swapping Oja for NLMS in one memory update path and rerunning the same forgetting benchmark as H-A3, in a setting where weights are actually shared (not per-concept-isolated) — that's the setting AURA_GENESIS never tested.

**Validation result (2026-07-23 campaign): SUPPORTED in exactly that never-tested shared-weight setting, with its failure mode now named.** In the H-A3 benchmark, matrix NLMS posts the best capacity curve of every candidate (100% recall through N=512, 51% at N=1024, graceful decline, no catastrophic cliff) — clearly better than pure Hebbian (cliff to 0% at 1024) and *vastly* better than the flat-decay Hebbian production form (65.6% already at N=128, worst curve measured). The cost: strongest recency bias past capacity (write-order quartiles 0/11/93/100 oldest→newest) — NLMS forgets oldest-first, LRU-like. As a cheap upgrade over Oja: yes. As zero-forgetting: no. `validation/exp_a_forgetting.py`.

**H-A5 — An external episodic store can complement, not replace, a fixed weight-based memory layer.** Source: GrillCheese's `capsulememoryintegration.md` (833 lines, full read) — a hippocampus-inspired design: Dentate-Gyrus-style sparse expansion (32D→128D, ~2% top-k winner-take-all) feeding CA3-style FAISS pattern completion, with importance-scored eviction (`score = consolidation_priority · stability · (recency + log(access_count))`, top 80% kept, protected items never evicted). STATUS.md corroborates a running instance (97 memories stored). This is architecturally a complementary-learning-systems split (fast episodic store outside the weights + slow weight-based consolidation), the same philosophy as Memorizing Transformer/MemGPT — it never touches synaptic plasticity at all, so it's orthogonal to, not competing with, the Hebbian fix. Status: PLAUSIBLE as a complementary mechanism, not a fix for the underlying problem. One documented weakness: the residual-stream injection hook (tiling a 32D vector across a 3072D residual stream with no learned up-projection) is methodologically weak; the text-context injection half is more credible. **Validate** by prototyping the DG-style sparse-expand + pattern-completion step as a side channel and measuring whether it reduces pressure on the weight-based memory — explicitly not a substitute for fixing that memory.

**Validation result (2026-07-23 campaign): mechanism VERIFIED at toy scale.** DG-style expansion (8× up-projection, 2% WTA) over a Hebbian store, with a *size-matched dense control*: at N=512 associations both dense variants collapse to 0% recall while the sparse code holds 100% — pattern separation, not parameter count, buys ~2× capacity (its own cliff arrives at N=1024). Also observed: dense Hebbian fails as a cliff (100%→0% between N=256 and 512), not a graceful curve. Complement framing confirmed. `validation/exp_a5_sparse.py`.

**H-A6 — Negative-result flag: no sibling folder has a validated fix for this problem.** All four surveys converge on the same finding. GrillCheese's own production Hebbian layer (`grillcheese/backend/brain/gpu_brain.py::hebbian_update`) implements `ΔW = η·⟨pre⊗post⟩ − λ·W` — a flat decay term, not true Oja normalization (no `post²·W` term, no norm-convergence guarantee) — the same failure class CubbyLLM is trying to fix, with a documented live shape-mismatch bug in the same function. Its own `forreview/capsules/DECISION.md` lists "Add EWC for continual learning" as still-open future work. Grepping GrillCheese's entire `learning/` package turns up no EWC, no orthogonal projection, no replay-based consolidation — only a crude activation-threshold "neuronal growth" heuristic, loosely adjacent to SPHeRe's structural-projection idea but untested against it. Novel_GNN_Arch's closest analog, `apply_outcome_update()` (importance-gated plasticity — a per-memory-slot effective learning rate driven by a plasticity trait and a simulated reward-prediction-error signal), is a well-shaped design sketch conceptually close to Elastic Weight Consolidation applied at memory-slot granularity, but it's ~250 lines of hand-tuned, duplicated-across-two-files demo code, tested only on 2–10 hardcoded synthetic records with randomly sampled (not task-derived) outcomes — zero quantitative forgetting-benchmark evidence either way. **Conclusion, not really a hypothesis: CubbyLLM cannot shortcut this problem by importing a sibling's solution. Budget real R&D time and benchmark every "reuse" candidate rather than adopting any of them on faith.**

**Validation result (2026-07-23 campaign): every sub-claim fact-checked by direct file reads and CONFIRMED**, with three precision fixes: GrillCheese's flat-decay update is at `gpu_brain.py:376` exactly as described, but the documented shape-mismatch bug is filed against its *caller* (`unified_brain.py::_update_hebbian_weights`, per `gcheese-faiss/CRITICAL_ISSUES.md:104-110`), not `hebbian_update` itself; `apply_outcome_update()` is ~38 lines duplicated across two files (not ~250 total); and the nuclear-test demo uses fixed ±0.8 outcomes — only the extended demo randomizes. Zero grep hits for EWC/elastic/orthogonal/replay/consolidat/fisher across GrillCheese's `learning/` package, and `DECISION.md:241` lists EWC as future work, both confirmed verbatim. The negative result stands at full strength.

**H-A7 — The learning gate: weight updates from live data enter the trunk only through a nightly, pre-registered promotion rule composed from harnesses that already exist — and that rule can tell a forgetting update from a clean one. Added 2026-08-28.** Source: the oracle-competition scoring (`docs/research/2026-08-28-oracle-competition-scored.md`), whose blind round produced the industry-default learning loop and a prior-art list none of which was in this repo. Context: `docs/ARCHITECTURE_VISION.md` lists the learning-gate as `[far]` ("vetted sources, anomaly detection, rollback") with no hypothesis entry, no kill criterion and no experiment — the one piece of the continual-learning story with no measurement path. H0 says *how* weights may depend on context; this entry says *when* a candidate update is allowed in at all. Prior art to build from (all ≤ 2025, IDs verified by the competition's own search passes, not re-verified here): **KTO** (Ethayarajh et al. 2024, arXiv:2402.01306 — learns from unpaired binary 👍/👎, the feedback a product actually produces); **O-LoRA** (Wang et al. 2023, 2310.14152) and **Online-LoRA** (Wei et al. 2024, 2411.05663) — orthogonal-subspace / task-free forgetting control for adapter-shaped deltas; **experience replay** (Rolnick et al. 2019, 1811.11682); the **ripple-effect test** for knowledge edits (Cohen et al. 2023, 2307.12976) as the regression suite an edit must pass; **TracIn** (Pruthi et al. 2020, 2002.08484) as per-update influence tracing — `git blame` for a promoted delta; **conformal LM** (Quach et al. 2023, 2306.10193) for the abstention contract; **sleep-time compute** (Lin et al. 2025, 2504.13171) for the always-on consolidation slot. Claim, concrete — promote candidate a_{t+1} iff every term holds: Δ general-capability regression ≥ 0 (H-G4's `socratic_test_text.jsonl` harness); Δ dated-key forgetting ≥ 0 against the NLMS curve (H-G2's NYT harness); in-window needle recall ≥ 95% (H-D4's `exp_needle_recall.py`); binding-channel retrieval ≥ 70% (H-B6's offline probe); claimed-answer precision ≥ 0.99 (the CoT pipeline eval); routing precision ≥ 0.90 (the margin gate). Every term is a measured artifact today; every candidate run writes a manifest (data hashes, seeds, base-checkpoint hash, delta hash) and is rollbackable by construction because deltas are never merged destructively. Two measured reasons the gate is not paranoia: H-B6 (a self-grading objective Goodharts while its loss looks like progress) and H0 part 2 (online-trained routers collapse) — so nothing the model scores itself ever enters, only execution-verified or human-thumbed signal. **Validate** (cheap, 151M checkpoint, CPU-tolerable): build the gate as one script over the existing harnesses and feed it three known deltas on `hd5_mem21.pt` — (a) a deliberately-forgetting update (plain SFT on one narrow slice, no replay: the H-A1 failure shape), (b) a matched update with replay + hardening, (c) the all-zero delta as the null; record which gate fires, at what margin, and the wall-clock. **Kill:** if the composed gate cannot separate (a) from (b) at any threshold the individual harnesses support — passes the forgetting arm or fails the clean one — then the harnesses measure the wrong things for update admission and the learning gate needs its own benchmark before any nightly path is built; second kill: if a full gate pass exceeds a nightly budget (~1 GPU-hour at 151M) it cannot be nightly and must be tiered (cheap gates every night, expensive weekly). Status: **RAN 2026-08-30 (Colab A100-40G) — the gate SEPARATES: at the nightly LR where a 3.3M-token replay update is CE-neutral on every source (3e-5, and 1e-5), the code-only update is still rejected with the mechanism named. Read that way: `t-ctx` reaches **linguistics 0.500** against a 0.0394 baseline (**12.7×**) and **language 0.400** against 0.0502 (8.0×), but **physics 0.0357 against 0.2975 — 0.12×, far *below* chance for that domain**, where `ref` reaches **0.738** (2.5×). `ref`'s **linguistics 0.833** is likewise a **21×** multiple of its baseline, a much larger one than its headline physics 0.738 — the flat-baseline reading had these two backwards. **8 of 15 `t-ctx` domains score exactly 0.0**, which is a weaker signal than it looks for the small ones (a 10–12 member domain's baseline is only 0.032–0.039, so a single miss-free run is unremarkable) and a strong one for `physics`, whose 0.298 baseline makes 0.0357 a real deficit. The overall shape still holds: a general-text LM with real language signal and essentially none on symbolic notation, which is most of what this corpus is made of. Contextual pooling does beat bag-of-embeddings, so the trunk body contributes something — just nowhere near enough to serve as a routing encoder, which it was never trained to be.

**What follows for M3 is a component boundary, not a repair job.** The question is not "how do we fix the trunk" — **M2 measured nothing about generation, so none of this is evidence about the trunk's performance at its actual task, in either direction** — but that **the routing encoder is a separate component from the trunk**, and M2 has now costed the alternatives. Three candidates, in rough cost order. **(a) A small purpose-built or fine-tuned encoder**, which the `ref` arm sizes — and the size comparison has to be **like-for-like**, which the obvious "22M beat 153M" phrasing is not. MiniLM-L6-v2's **22.7M total** reaches macro 0.3580 where the trunk's **153.4M total** reaches 0.0962; but **131.1M of the trunk's total is two untied `127996 × 512` vocab tensors** (2 × 127,996 × 512 = 131,067,904 of 153,383,440), leaving a **22.3M body** — against MiniLM's own **11.0M body** (the remaining 11.7M being its word-embedding table). **The honest read cuts both ways:** the trunk is not 6.8× the size of the thing that beat it, so raw scale does not explain the loss; but its *body* is still about **2× MiniLM's body** and loses by 3.7×, so "it is merely smaller" does not explain it either. (Counts derived from the pinned checkpoint's own tensor shapes — identity stamped in `exp_f2m2_stage1.log` — and from the pinned `sentence-transformers/all-MiniLM-L6-v2`; the design spec's §3 makes the same body-vs-total point.) **(b) The training-free lexical route**, which is cheaper than it looks — see the `ngram` result above and the mechanical note there: `ngram` and `hash` share the *same* BLAKE2b machinery, so the finding is that **whole-string** hashing destroys locality, not that BLAKE2b does, which makes upgrading `WorldEncoder._hash_to_vec` inside the existing hash architecture a near-free lever rather than a rewrite. **(c) A trained projection head *on top of* the trunk** — the only option that reuses the trunk **legitimately**, by learning the encoder interface rather than assuming mean-pooling already is one. Note that (c) is also the only one that keeps a single model serving both roles, which is what the θ=f(c) story wants; M2 says nothing about whether it works, only that it is the honest form of the question.

**Uncomfortable control: a training-free lexical sketch beats the trained trunk.** The `ngram` arm — character-trigram block codes bundled by superposition, **no model, no training, no projection**, born directly in block space — reaches **macro 0.1400 = 2.10× chance** with self-retrieval **0.100** (`exp_f2m2_stage1.json`), beating both trunk arms and being **the only non-`ref` arm to clear the 2×-chance bar that bar 3a asks of the trunk**. Its macro is **+8.2 sd above the matched noise null of 0.0599 ± 0.0098** (`validation/logs/exp_f2m2_null_baseline.json`), so the win is real and not a baseline artifact. **The qualifier this branch's own micro/macro correction demands: `ngram` is mid-pack on micro and below `hash` there** — 0.1036 against `hash`'s 0.1179, and **−2.7 sd below the matched micro null of 0.1226**. So the honest claim is narrower than "the sketch beats the trunk": it beats both trunk arms on the **macro** metric and on self-retrieval, while its **micro** sits below the random-encoder floor like every non-`ref` arm. Macro is the metric the kill criterion uses and the one that is not dominated by physics's 30% share, so the comparison stands — but it is a macro claim, not a blanket one. Two consequences, both honest ones. (a) `hash` should not be presented as the only baseline the trunk had to clear: `ngram` is a *stronger* training-free null, and the trunk loses to it. (b) M3's question is therefore not just "fine-tune an embedder" but **"why does a next-token LM carry less domain-routing signal than raw lexical overlap?"** — a question about what the objective builds, not about model quality. **(c) The mechanically important detail, easy to miss: `ngram` and `hash` share the *same* BLAKE2b machinery** — identical `blake2b(..., digest_size=8)` → `int.from_bytes(..., "little") % 2**63` → `default_rng(seed).integers(0, L, size=K)` seeding and index draw (`validation/exp_f2m2_semantic_routing.py:115-147`). They differ in exactly two ways: `hash` hashes the **whole string** and *assigns* one-hot, while `ngram` hashes **character trigrams** and *accumulates* (bundles) them. So the premise M2 confirmed is **"whole-string hashing destroys locality," not "BLAKE2b does"** — and the fix lives inside the existing hash architecture rather than replacing it, which is why this is the cheap lever in M3's option (b) below.

**Discretization is INCONCLUSIVE — and M2's earlier "quantization preserves, even improves, routing" claim is RETRACTED.** The shipped Stage-2 numbers ordered **`pq-adc` 0.4188 > `pq` 0.3719 > `dense` 0.3580 > `argmax` 0.3133** on `ref` (`exp_f2m2_stage2_ref.json`) and the same way on `t-ctx` (**0.1068 > 0.1030 > 0.0962 > 0.0736**, `exp_f2m2_stage2_t-ctx.json`), with bar 4 recorded PASS on both. Review found the cause: **the PQ codebook was fit on the very items leave-one-out exists to exclude.** At 280 axioms over `L=128` centroids that is ~2.2 points per centroid, so a candidate's reconstruction can carry a fraction of the query's own formula — a channel `dense` does not have. The tell was already in the table: `argmax`, the only discretizer with no fitted codebook, was the only variant that *lost* to dense. Two controls followed (`exp_f2m2_leakage_ref.json`, `exp_f2m2_leakage_t-ctx.json`), both logging the verdict `"gain FAILS both controls -- shipped result was leakage"`. Under the **item-disjoint control** (fit on a stratified half, score only the other half, `n_scored = 146`) **the ordering inverts and PQ collapses**: on `ref`, `argmax` **0.3281** now beats `dense` **0.3017** while `pq` falls to **0.1971** and `pq-adc` to **0.2116**; on `t-ctx`, `pq` **0.0828** and `pq-adc` **0.0778** fall below `dense` **0.1276** (`argmax` **0.1149** sits just under dense there, so the argmax-overtakes-dense inversion is `ref`-only). **What is unanimous across both arms is that `pq` and `pq-adc` drop below `dense` once the codebook cannot see the scored items.** The **source-disjoint control** (codebook fit on the `name` view) is mixed and arm-specific: on `ref`, `pq-adc` 0.3874 > dense 0.3580 but `pq` 0.3378 < dense; on `t-ctx` the two swap (`pq` 0.0976 > dense 0.0962, `pq-adc` 0.0821 < dense). **Do not read this as "PQ hurts" either.** Neither control is clean — the name-fit control confounds surface modality (it fits on natural language and scores symbolic notation), and the half-split control's codebook is fit on ~134 points across 128 centroids (~1.05 per centroid), degenerate enough that it may *understate* PQ. **The correct conclusion is that this corpus cannot settle the question**, with a concrete requirement for one that can: **n ≫ L — at least ~1280 axioms for L=128 — with a fit set disjoint from the scored items.** ADC remains architecturally sensible on its own terms (only the stored side must be one-hot to participate in `bind`/`bundle`; a routing query never needs quantizing) but it has **no evidence of improving routing**. The one dense-vs-one-hot fact that survives the disjoint control is bar 4's actual question — one-hot-per-block does not *destroy* routing relative to dense, though under control B that holds via `argmax` (0.3281 vs 0.3017 on `ref`; 0.1149 vs 0.1276, still ≥ 0.80× dense, on `t-ctx`), not via `pq`. **A note on the two exported artifacts, because they outlived the conclusion they encode:** `data/axiom_embeddings_ref.npz` and `data/axiom_embeddings_t-ctx.npz` store the Stage-2 embeddings together with `discretization="pq"`, that variant's `tau_match`, and `centroids` — *the leakage-contaminated codebook itself*. They are a **record of what the screen produced, not a configuration to load**: nothing in CubbyLLM or mowm reads them, and the only consumer they were ever written for (the mowm-side semantic path, the plan's Task 7) was gated out by the Stage-1 kill criterion and never built. Both files now carry that retraction as `note`/`retracted` string fields **inside the npz** so a future reader cannot lift `tau_match` or `centroids` out of them without seeing it.

**The ROC-AUC null on this corpus is ~0.11, not 0.5 — so the earlier "every AUC is below 0.5, therefore nothing separates" reading is WRONG, and correcting it makes the arms look better, not worse.** AUC here is the pooled, unpaired Mann-Whitney statistic over all same-domain maxima against all different-domain maxima. But `same_cos[i]` is a **max over the (n_d − 1) same-domain candidates** while `diff_cos[i]` is a **max over the (n − n_d) different-domain candidates** — roughly **14 against 265** on this corpus — and the max of more draws is stochastically larger, so this statistic's null sits **far below 0.5 by construction**. That is a property of the candidate sets, not a diagnosis of the encoders. Measured rather than argued: pushing a **pure-noise encoder** through the *shipped* `loo_domain_routing` / `recalibrate_tau` over the real corpus's domain structure, 10 seeds, gives an AUC null of **0.1133 ± 0.0072** in the dense code format and **0.1605 ± 0.0162** in the one-hot format (`validation/logs/exp_f2m2_null_baseline.json`). The control that proves it is a candidate-set-size artifact: on a **balanced** two-domain structure over the same 280 items (≈139 against 140 candidates), the same noise gives **0.5131 ± 0.0191** — 0.5, exactly as an AUC null should be when the two candidate sets are the same size.

**Against that measured null, six of the eight recorded AUCs show real separation, one is marginal, and one is genuinely below chance.** Reading each variant against the null for its own code format (`dense` and `pq-adc` compare continuous vectors → the 0.1133 null; `argmax` and `pq` compare one-hot codes → the 0.1605 null): on `ref`, `pq-adc` **0.454** (≈ +47 sd), `dense` **0.430** (≈ +44 sd), `pq` **0.427** (≈ +16 sd) and `argmax` **0.358** (≈ +12 sd) all sit far above; on `t-ctx`, `pq-adc` **0.246** (≈ +18 sd) and `dense` **0.227** (≈ +16 sd) do too; `argmax` **0.182** is **marginal** (≈ +1.3 sd, only just past the null's observed maximum of 0.180); and `pq` **0.0915** sits **below** its null (≈ −4.3 sd) — the one arm the original blanket claim actually holds for, and notably the variant whose τ of **0.850** comes from the leakage-contaminated codebook retracted above (`exp_f2m2_stage2_ref.json`, `exp_f2m2_stage2_t-ctx.json`, nulls from `exp_f2m2_null_baseline.json`). So the honest statement is **`ref` separates strongly, `t-ctx` separates weakly but really, and only `t-ctx`'s `pq` is at-or-below chance** — not "nothing separates."

**What survives, on better grounds: no M2 number is a usable `tau_match`, and M1's `0.35` is not replaced by any of them.** Separation being above its null is not the same as a transferable threshold, and four independent reasons block the transfer. (a) **The τ values live in incomparable spaces**: `t-ctx`'s `pq` τ of 0.850 is a one-hot block-code cosine (81 levels at K=80), its dense τ of 0.257 is a continuous cosine, and M1's 0.35 is a k=4/l=32 one-hot cosine (five levels). (b) The **corpus is cross-modal** (`name` against `formula_str`), so its same/different distributions are not production's. (c) The `pq` τ specifically is an artifact of the **retracted** leakage result. (d) Even the best AUC here, `ref`'s 0.454, is weak *in absolute terms* — a screen result, not a calibration. Treat every τ in `exp_f2m2_stage2_*.json` and in the exported `.npz` files as a record of what this screen measured, never as a setting to load.

**The corpus poses a harder task than production would — a calibration caveat on bar 2, not an excuse.** Even `ref` reaches only **0.229** self-retrieval (`exp_f2m2_stage1.json`), because the cross-view design pairs natural-language `name` against symbolic `formula_str`: a **cross-modal** match, harder than routing a natural-language question to a domain. Bar 2's 0.50 was calibrated for a same-modality task, so read that FAIL as diagnostic rather than decisive — while noting the caveat was written *after* the run and retroactively softens a bar that failed. The metric also has a ceiling below 1.0: two `name` values (*De Broglie Wavelength*, *Boltzmann Distribution*) each appear twice with different formulas, embed identically, and share one argmax, so self-retrieval tops out at **278/280 = 0.993** (`validation/exp_f2m2_semantic_routing.py:339-346`, `self_retrieval_top1`'s docstring). This points at a cheap first M3 experiment before concluding the embedder is the bottleneck: encode axioms from **combined** text (name + domain + formula) and pose natural-language questions against them — the production shape — rather than name-against-formula.

**Four methodology corrections, recorded because this is exactly what rots silently — and one error class caught three times.** (a) The kill criterion compared **macro** accuracy against the **majority-class rate (0.300)**, which is a *micro* baseline. Macro-averaging removes class imbalance by construction, so every constant classifier — the majority-class strategy included — and uniform-random guessing all score exactly `1/n_domains`. The category error made bar 1 trivially satisfied and set bar 3a at an unreachable macro of 0.600; against the correct macro-chance of 0.0667 the bars become 0.0800 exactly (near-binding, actual 0.0747) and 2/15 = 0.1333… (reachable, actual 0.0962). Both chance levels and both actuals are in `exp_f2m2_stage1.json` (`micro_chance`, `macro_chance`, `arms.hash.macro`, `arms.t-ctx.macro`); the two bounds are `1.2 ×` and `2 ×` macro-chance per the design's §4.2. **The measured verdict did not change** — the bars were wrong, the answer was not. (b) The design spec claimed challenges were also posed in the reverse direction; **they never were** (`run_stage1` measures name→formula only, and both directions share one symmetric cosine matrix), so the claim was dropped from the spec rather than quietly left standing. (c) **The whole-branch review found (a) recurring in three more places** — ROC-AUC read against 0.5, micro read only against the majority-class rate, and per-domain recall read against one flat number, when each of those statistics is an **argmax over ~279 candidates** whose null is set by candidate-set sizes rather than by class priors. All three are now measured rather than assumed, with a **pure-noise encoder** pushed through the *unchanged* shipped metrics over the real corpus's domain structure and over a **balanced** control structure, 10 seeds each (`validation/exp_f2m2_semantic_routing.py --null-baseline` → `validation/logs/exp_f2m2_null_baseline.log` / `.json`). The measured nulls: **AUC 0.1133 ± 0.0072** dense / **0.1605 ± 0.0162** one-hot on the corpus structure against **0.5131 ± 0.0191** on the balanced one; **micro 0.1232 ± 0.0074** (analytic 19/155 = 0.1226); **macro 0.0599 ± 0.0098** dense / **0.0666 ± 0.0125** one-hot (analytic 53/837 = 0.0633, close to but not equal to the 1/15 the bars use); **self-retrieval 0.0032 ± 0.0026**. **Two of the three corrections made findings stronger, not weaker** — `hash` routing at chance became a direct measurement, and `t-ctx`'s micro turned out to be *below* the random-encoder floor — while the third **reversed** a claim: "no arm separates same-domain from different-domain" was an artifact of the 0.5 null and is retracted above. The lesson is the one this milestone had already learned once at bar 3a: **a metric's baseline is a property of the metric's own procedure, and must be derived (or measured) from that procedure, not borrowed from a familiar number.** (d) **The same species of error at the level of the design rather than the statistic: bar 3b (`trunk ≥ 0.60 × REF`) and the decision rule's "ship the trunk" branch treated the trunk as an *embedder candidate*, which the architecture never claimed it was.** The trunk's role is generation and carrying context for θ=f(c); it has no similarity, contrastive or retrieval objective in its loss, so a bar asking it to come within 0.60× of a purpose-trained sentence encoder was measuring it against a standard that was never the right one — a *category* mismatch, exactly like (a) and (c)'s *baseline* mismatches, just one level up. **The bar's FAIL verdict stands and its consequence was correct** (do not wire a semantic path the screen showed does not route), but the right reading of the FAIL is "an LM trunk is not a retrieval encoder," not "our trunk underperformed." **Three instances of one error class in one milestone is itself the finding**: whenever this project compares a measured thing to a reference, the next question should be *is this reference the right null/standard for this exact procedure?* — asked before the run, not after it.

**Two supporting measurements, from the screen's own self-test (`validation/logs/exp_f2m2_selftest.log`).** The orthonormal projection is cosine-exact as designed: the self-test asserts `max|Δ| < 1e-5` between pre- and post-projection cosine matrices (`validation/exp_f2m2_semantic_routing.py:852-857`, inside `self_test`) and measures **8.77e-09**, ~3 orders inside the bar. Note the **assertion bound is the enforced claim**; the printed value is the measurement it passed by, not a separately guarded invariant. Separately, `t-ctx` is strongly **anisotropic** — unrelated-sentence cosine **0.756**, against `t-bag`'s **−0.019** — i.e. mean-pooled LM hidden states occupy a narrow cone. That is a *candidate explanation* for weak routing (a centering/whitening step is the standard remedy, and an M3 candidate), **not** evidence of structure, and it is corroborated independently by the logged τ 0.850 / AUC 0.0915 fingerprint above. Every figure in these paragraphs links a file in `validation/logs/`.

**H-F2 M3 fast-encoder screen (2026-08-07) — 0.86–0.95× the teacher's routing quality with no model in the challenge path.** The user set the binding constraint directly: embedders are too slow for serving, so the challenge-side encoder must be model-free (axioms are encoded offline regardless, per H0's frozen shape). Measured on the same 280-axiom LOO screen against the same matched nulls, with per-challenge latency: **(1) model-free lexical arms** — words+IDF reaches macro **0.1730** (2.73× null) at **~19 µs**, BPE token-ids+IDF **0.1520** at ~29 µs using ids the pipeline already holds, and a K-sweep 80→320 buys only +6% relative at 4× memory, so dimensionality is a mild constraint rather than the lever (`exp_f2m2_fast_arms.{log,json}`). **(2) BEAGLE distributional memory is a NEGATIVE** — accumulating each token's co-occurrence neighbors over 200M wiki_full tokens *degrades* routing (pure memory 1.0–1.3× null; self-retrieval collapses to 0.025; blending the signal back recovers only partway, 0.1204): superposition smears exactly the surface-overlap signal this task runs on. Winner: **macro 0.3407 (5.38× null) = 0.95× the live teacher at ~25 µs/challenge** — ~350× faster than the teacher's 8.9 ms single-query — with every ingredient attributable (words-over-tokens; −PC1 +0.067; +signal +0.021; learned-over-random table values ≈ 2×) (`exp_f2m2_m2v.{log,json}`). **Honesty check passed:** refitting IDF and PC1 on external wiki_full text (20k docs; 744/848 axiom words covered) drops the winner to **0.3079 (4.86× null, 0.86× teacher)** — the in-domain statistics were worth ~0.033 and the result survives out-of-domain stats (`exp_f2m2_m2v_ood.{log,json}`). Caveats: the benchmark is the same 280-axiom cross-modal screen (its caveats above apply); latencies are unoptimized Python (the Rust VM / Vulkan path can only lower them); no τ here is a transferable operating point (the τ-caveat paragraph above applies unchanged, and route-misses fall through to spawn, so routing errors are soft). **Wired into mowm** as `mowm/encoding/semantic_words.py` — an offline `build`/teacher pass and a serve-time `FastWordEncoder` that imports only numpy.

**H-F2 M3 scale + memory-pathway evals (2026-08-07) — the haystack curve and the injection/chase result.** Two follow-on evals on the production table, both on E:\valid_scaling_law_with_facts.pq (10k multi-hop questions; every row's answer verified to live in its final supporting fact, and its designated `fact_to_inject` verified present in the chain, 10000/10000) with DBpedia abstracts as distractors. **(1) Haystack** (`exp_m3_haystack.{log,json}`; 400 questions, 636 target facts): the dense form is flat to 100k distractors (any-supporting-fact hit@1 0.978→0.973; MiniLM anchor 0.993), and the **compact 80-byte form** (argmax index per block — the qFHRR integer-phase reading, ADC-scored with no fitted codebook) degrades gracefully to **0.713 hit@1 / 0.920 hit@20 at 1M documents**, having encoded the 1M store in ~9 min (543 µs/doc) vs ~30 min for the batched teacher — implying the two-stage serve shape: compact shortlist@20 + dense re-rank. **(2) Injection accessibility + multi-hop chase** (`exp_m3_injection.{log,json}`; 800 questions): once a fact is injected into the store, the question reaches it top-5 at **0.616 = 0.95× teacher** (0.649) — but both encoders sit on the same **surface-form cliff by hop** (table 0.995/0.289/0.226 across 1/2/3 hops; teacher 1.00/0.34/0.30): intermediate-hop facts share only ~55% of their words with the question (vs ~75% at hop 1), so the cliff is the task's, not the table's. Robust at scale: +100k distractors moves inject hit@1 0.481→0.480. **The notable finding: iterative chase** — n_hop rounds of top-1 with the retrieved text appended to the query, still pure table lookups — lifts full-chain recovery 0.665→**0.733** (3-hop 0.195→**0.371**, paired ~1.9× on the same questions, on a budget of only n_hop picks vs single-shot's top-20), while **the identical protocol does nothing for MiniLM** (0.719→0.720), leaving the chased table at parity with the chased teacher. Query expansion is the natural multi-hop mechanism for a bag-of-words encoder — each retrieved fact donates the bridging entity words the question lacks — where appending text to a sentence-encoder query dilutes as much as it informs. Honest bounds: per-hop table-vs-teacher differences are within noise at n=159 (3-hop); the load-bearing claims are the paired improvement and the protocol asymmetry. (1) **The note's proposed "expand to k=32, l=256 (d=8192)" should instead be the shape already decided in H-B5: k=80 x l=128 = d=10240.** cubemind runs I-RAVEN at k=16 x l=128 = d=2048, i.e. 5x under the standardized algebra. (3) **Hierarchical bundling is not a new fix; it is H-B4, and it only works with cleanup between levels.** Bundling objects into rows and then rows into a panel is exactly the chained F=2 decomposition described above, already VERIFIED at 100% accuracy from depth 1 to depth 20 in `cubby-concepts/vsa/graph.py`'s `SequentialHyperGraph`. Without a cleanup step between levels, hierarchical bundling merely redistributes the same total crosstalk across two hops and buys far less than it appears to. Port the SequentialHyperGraph pattern, not just the two-level idea.

Also note the regime: I-RAVEN objects share attribute vocabularies (shape/colour/size), so the fillers are **correlated**, not quasi-orthogonal. H-G2 measured that penalty directly — real keys ran 3.1x more correlated than random bipolar and cost every candidate 2-3x recall. Capacity here is therefore worse than random-vector math predicts, which is consistent with 9 items straining a space where H-B6's probe held ~97% retrieval at n=16 on quasi-orthogonal trunk features.

**KILL CRITERION TRIGGERED (2026-08-02) — H-B6 IS FALSIFIED. The aux loss was Goodharted; do not use it.** The offline probe (`validation/exp_b6_blockcode_transfer.py`, gate passed: it reproduces the run's own objective at cos 0.840 vs the logged 0.842) added the metric the training loss never had — **retrieval accuracy**, i.e. can you tell *which* filler was bound. The loss rewards cosine-to-own-filler and never penalizes cosine-to-*other*-fillers, so **collapsing every hidden state in a sequence onto one direction scores ~0.86**. The trained model sits exactly on that curve. So the earlier "bind 0.735→0.158" was real as a number and meaningless as a capability: it measured collapse, not bindability. The "+0.088 BlockCode transfer" the probe reported is transfer of the collapse artifact — the verdict line said POSITIVE because it keyed on cosine delta and ignored retrieval; that heuristic is wrong and is being changed. **The deeper finding, and the reason no fix is worth building: an untrained trunk is ALREADY a near-optimal VSA substrate.** Random high-dimensional vectors are quasi-orthogonal by construction — that is the property hyperdimensional computing is founded on — so retrieval starts at 96–98% and there is nothing for a binding objective to add. A discriminative (InfoNCE-over-the-bundle) reformulation was built and tested: it *prevents* the collapse (filler-filler stays ~0.00, retrieval 96–98%) but leaves cosine pinned at the 1/sqrt(n) crosstalk floor, i.e. it buys **nothing over random init**. **CONFIRMED ON A TRAINED CONTROL (2026-08-02, `exp_b6b_ckpt_ab.py`).** `ckpt_1` — same corpus, same architecture, 7,500 steps, binding loss OFF — scores **96.9% retrieval** with filler-filler cosine **0.276**, against the binding-trained checkpoint's **11.9%** and **0.934**. Its binding cosine is 0.243, i.e. exactly the 1/sqrt(16) crosstalk floor, as expected for a trunk that never saw the objective. **This exonerates the architecture**: the theta=f(c) memory layer, the MinGRU trunk and the hybrid vocab all preserve retrieval fine — the aux loss alone causes the collapse. It also gives the healthy baseline for real (not random) features: modest within-sequence correlation ~0.28 is harmless; it is the jump to ~0.93 that destroys discrimination. The language-modelling half of the A/B is **permanently unanswerable from these artifacts** — the checkpoints are 20,000 vs 7,500 steps and the run overwrote a single checkpoint path, so no matched-step binding checkpoint exists (held-out bpc 1.0722 vs 1.3924 is dominated by the 12,500 extra steps and attributes nothing). Moot for the decision, since the loss damages the channel it was meant to build. **Action: set `bind_weight=0` for the DDP run.** Everything below this line describes the falsified configuration and is retained as the record of how it looked before the retrieval metric existed. `validation/logs/exp_b6_blockcode_transfer.log`.

**Run completed (2026-08-01).** The same run finished its full **20,000-step** cosine schedule (LR decayed to the 3e-5 floor; ~123M tokens, ~3.9h wall, peak 92.5GB). Over the complete run `bind` did **not** stop at the 0.20 plateau — it kept slowly descending to **~0.158** (cos recovery ~0.84) while `bpc` improved to **~1.1**, the two curves tracking together the entire way with no divergence at any point. ## 5. Group C — Vocabulary, tokenization, and the softmax bottleneck (a core design requirement, not an optimization)

**Reframed 2026-07-23.** CubbyLLM's vocabulary will be significantly larger than cubby-lm's 32k — explicitly *because* the mechanisms below can remove the full-vocabulary softmax step that would otherwise make a large vocab expensive to train and serve. Everything in this group graduates from "worth checking if it helps" to "the output-head mechanism CubbyLLM's vocab strategy actually depends on." The open question is no longer whether to pursue this, it's which specific mechanism, and how large "much larger" ends up being — both still genuinely open (see H-C6).

**H-C1 — Dynamic hyper-encoder embeddings are the enabling mechanism for a much larger vocabulary, not an optional parameter-count optimization.** Source: ZeTT (hypernetwork predicts token embeddings for any target vocabulary on the fly) and zip2zip, motivated by the observation that static embedding/unembedding tables scale linearly with vocab size and can reach up to 93% of total model params in typical LLMs at 100k+ vocab — the exact regime CubbyLLM is now explicitly targeting, unlike cubby-lm's comparatively modest 32k. Status: SPECULATIVE mechanism (ZeTT/zip2zip are external research, not yet reproduced against CubbyLLM's actual target scale), but no longer optional to check — it's close to a load-bearing assumption behind the vocab requirement itself. **Validate** by prototyping a hyper-encoder generating embeddings on the fly for a synthetic vocabulary at the target order of magnitude, and confirming (a) generated-embedding quality is competitive with a static lookup table at a small/medium vocab size where both are still cheap enough to compare directly, and (b) the hyper-encoder's own compute cost per token doesn't reintroduce the cost problem the static table was supposed to avoid. **Kill criterion:** generated embeddings measurably underperform static ones at matched vocab size, or the hyper-encoder's forward cost scales badly enough to erode the "fast" half of the goal — either result means the large-vocab requirement needs a different enabling mechanism, or a smaller target vocab after all.

**Validation result (2026-07-23 campaign): kill criterion HALF-triggered at toy scale.** On the real spm32k token stream (cubby-lm valid.txt, V=8k kept, d=64, identical budgets): the **quality clause FAILS** for a pure surface-form generator — static table val loss 3.886 (ppl 48.7) vs char-CNN hyper-encoder 4.389 (ppl 80.6), +0.50 nats; surface form alone cannot recover what a table memorizes. The **cost clause PASSES decisively** — 1.26µs/token to regenerate the full table, cacheable at inference, embedding params V-independent (77k vs 578k). Read alongside zip2zip's actual design (static base vocab + composed hypertokens), this steers toward a **hybrid** (static core + generated/composed tail), not pure generation — see H-C6. Toy-scale caveat stated in the log; re-check at target scale before betting the vocab strategy. `validation/exp_c1_hyperencoder.py`.

**H-C2 — zip2zip-style LZW hypertoken compression reduces autoregressive step count 20–60%, directly improving latency.** Status: **VERIFIED (2026-07-23 campaign — measured on the real tokenizer, no model change).** grillcheese_spm32k_v2 over 8MB of cubby-lm's valid.txt (2.07M base tokens): **per-document (streaming-honest) reduction 22.2%** — the claimed range reproduced at its low end; a *persistent cross-document dictionary* reaches **53.4%–66.6%** (32k→992k hypertokens minted) — at/above the claimed top. The persistent-dictionary variant is the H-C6 dynamic-vocab question in disguise: ~22% is free, the rest is bought with exactly the machinery H-C6 would have to decide to build. `validation/exp_c2_lzw.py`.

**H-C3 — Removing the full-vocabulary softmax is the specific mechanism that makes a much larger vocabulary affordable at the output head.** The general pattern (retrieve top-K via an ANN index, softmax only over those, instead of a full-vocabulary softmax) is exactly what cubby-lm's `VSABindingHead` cosine-similarity-against-a-frozen-D=10240-codebook already did structurally, so it's not a foreign idea to graft on — it's an extension of something the predecessor already had the right shape for. GrillCheese's `gcheese-faiss/` module is a small-scale (sub-100k item) working existence proof this pattern is production-viable: a hand-written Vulkan GPU reimplementation of brute-force kNN (built because CUDA faiss-gpu doesn't run on their AMD hardware), running *side by side* with a separate softmax-attention memory-read path that they are actively optimizing — i.e., a real system where both approaches coexist and get compared. Status: PLAUSIBLE, and the clearest "this is already almost what we do" finding in the whole survey. Self-reported performance figures (sub-2ms @ 10k memories, 2-5x GPU speedup) are explicitly flagged by their own `CRITICAL_ISSUES.md` as unvalidated planning targets, not measurements. **This is no longer a formalize-what-already-exists nice-to-have — it's the specific mechanism the new, larger vocabulary is being designed around, so it needs validating at the target vocab scale, not at cubby-lm's old 32k.** **Validate** by building an explicit ANN-retrieval output head (or a Sylph-style sigmoid-decomposed alternative, per H0) at a representative large-vocab scale and benchmarking latency/accuracy against a full-softmax baseline at the same scale, not against cubby-lm's existing numbers.

**Validation result (2026-07-23 campaign): mechanism confirmed REQUIRED; bounds measured (CPU, batch=1).** Full-head cost is linear in V (measured 7.8× for 8× vocab at d=2560; 47.9ms/token at the real 32k×10240 shape). The retrieval floor (exact scoring over a K=1024 shortlist) is ~flat at 0.2–1.5ms — a **32× win at the real head shape**. Naive IVF over *random* codewords is the pessimistic bound and it's poor (37–80% top-1 agreement, falling with V) — index quality on *trained* embeddings is the real engineering question before committing to a specific ANN. The decisive number is memory: **V=1M fp32 codebook = 10–41GB** (d=2560/10240; the 1M row is explicit linear extrapolation, not measurement) — at large V the softmax bypass isn't an optimization, it's the only way the head exists. One correction to this hypothesis's framing: the current `VSABindingHead` does NOT avoid the O(V·D) cost — it's still a full-vocab matmul; it saves *parameters*, not compute. `validation/exp_c3_latency.py`.

**H-C4 — A trained flat-taxonomy domain classifier is a usable baseline for the "automatic specialization" routing half of the goal, not the end state.** Source: Novel_GNN_Arch's `capsules/domain_classifier.py` + `domain_head.pt` — a small (~570K-parameter), actually trained and evaluated 2-layer MLP (frozen sentence embedding → 512 → 88 sigmoid domain outputs, `scripts/test_domain_head.py` reports accuracy/Hamming-loss/F1, though the achieved numbers weren't reproduced this session, only the code and eval harness were read). Status: this is the single most mature, lowest-integration-risk artifact found anywhere across all four surveys — real weights, real eval script, minimal dependencies (`torch`, `transformers`, `scikit-learn`). But it routes into a fixed flat 88-domain taxonomy via a plain MLP, not a learned/generative specialist space — it's a stepping-stone baseline for H0's routing half, not the hypernetwork-based specialization mechanism itself. **Validate** by using it directly as a baseline router to benchmark any new context-conditioned routing mechanism against — this is close enough to drop-in that skipping it would be wasted effort.

**Validation result (2026-07-23 campaign): VERIFIED and executed end-to-end offline.** `domain_head.pt` loads with `weights_only=True` (clean tensor dict): exactly **569,944 params**, shapes 1024→512→88 matching the code. The eval harness ran on CPU against the shipped 3-record fixture (metrics print: exact-match, Hamming, micro/macro F1). Two precision notes: the module emits **logits** (sigmoid applied downstream; trained with `BCEWithLogitsLoss`), and the shipped `file_capsules.jsonl` is **0 bytes** — no headline accuracy is reproducible from the repo as shipped; embedding fresh text needs `BAAI/bge-m3` (1024-dim, not in the local HF cache — would require a download). Baseline: usable as claimed. Its historical metrics: unverifiable without regenerating a test set.

**Reinforced by H0 part 2 (2026-07-23):** the learned-context experiment (`exp_h0b_learned_context.py`) makes this artifact's role precise and load-bearing rather than optional. When H0's context is inferred by a router trained *online*, the router itself catastrophically forgets its own routing (slots collapse 6→3 distinct, task-0 confidence →37%) — so the context source **must be an offline-pretrained classifier over all domains**, which is exactly what `domain_head.pt` is (trained once on 88 domains). H-C4 moves from "stepping-stone baseline" to "the specific shape the routing half needs": upstream, pretrained, frozen at inference.

**H-C5 — Economics claims in cubby-concepts' `budget-hardware/` need scrutiny before use.** `revenues-simulation.txt` projects a $956M five-year valuation; the ~100–1000x cost-per-query claim lives in **`simulatorandprofitability.txt:138`** (citation corrected 2026-07-23 — `vs-Kimmy-K3.txt` contains no numeric multiplier, only "a fraction of the cost"). Directional motivation only — confirmed.

**H-C6 — CubbyLLM's vocabulary may not need to be a fixed-size discrete set at all.** Added 2026-07-23. zip2zip's inference-time LZW hypertoken compression and ZeTT's target-vocabulary-agnostic embedding generation both point toward an open-ended vocabulary — new hypertokens formed and embedded on demand, no fixed upper bound chosen in advance — rather than simply picking a bigger fixed number than 32k. Status: SPECULATIVE, and genuinely undecided: "much larger" could mean a large-but-fixed vocabulary (say 250k–1M, sized once, a more conservative extension of what cubby-lm already did) or an effectively open/dynamic one (no fixed size, tokens/hypertokens minted at inference time, closer to zip2zip's actual proposal). These have different engineering consequences and different new failure modes (a dynamic vocab risks unbounded cleanup-memory growth and variable novel-hypertoken quality; a fixed-but-large vocab reintroduces a version of the static-table cost problem at a bigger constant). **Validate** by deciding this explicitly as a design choice before implementation begins — it's not a detail to leave implicit, since H-C1's hyper-encoder and H-C3's softmax-bypass mechanism need to be built differently depending on the answer.

**Validation result (2026-07-23 campaign): decision package assembled.** Every measurement this campaign produced points the same way: H-G1 (fixed-vocab pipeline proven to 65,536, one order of magnitude of headroom demonstrated), H-C1 (pure surface-form generation loses +0.50 nats at toy scale; generation *cost* is negligible/cacheable), H-C2 (22% step reduction free; persistent hypertokens buy 53–67% but require dynamic-vocab machinery), H-C3/H-C7 (direct readout fine to V=1M; memory is the wall; retrieval head required either way).

**DECIDED (user, 2026-07-23): HYBRID.** Fixed core vocabulary — next step a 128k–256k BPE on the proven H-G1 pipeline — plus a retrieval output head from day one, with the hypertoken/dynamic tail deferred as a later, separately-gated addition. H-C1's hyper-encoder and H-C3's softmax-bypass mechanism should be scoped to this shape.

**H-C7 — A much larger vocabulary strains the VSA binding head's codebook capacity and needs its own sizing pass.** Added 2026-07-23, a direct consequence of combining H-B4's capacity law with this group's new vocab requirement. If the binding head's codebook doubles as the word-vocabulary representation (as in cubby-lm's D=10240 MAP-bipolar codebook, per the architecture map), the resonator-network capacity law verified in Group B (P_cap ≈ 0.64·D^(1/(F-1)), empirically ~80–100 distinguishable codewords per factorization slot at D=10000, F=3) means a significantly larger vocabulary may need a larger D, a re-architected codebook (e.g., compositional/factored token identities instead of one codeword per token), or a deliberate decision to keep the VSA binding space and the token vocabulary as two different-sized spaces connected by a projection, rather than one shared space. Status: SPECULATIVE — this hasn't been worked through as its own design question yet, it's a mathematical consequence of two already-gathered pieces of research meeting for the first time in this revision. **Validate** by computing the actual required D for the target vocabulary size once one is chosen (H-C6), against the same capacity formula already verified in cubby-concepts' test suite, before assuming cubby-lm's D=10240 sizing transfers to a much larger vocab.

**Validation result (2026-07-23 campaign): RESOLVED with numbers — the fear was aimed at the wrong place.** **Direct one-codeword-per-token readout does NOT strain at D=10240**: max-crosstalk grows only as √(2lnV/D), leaving a +0.50 cosine margin for a cos=0.55-quality query even at V=1M (empirically 100% top-1 at every V tested up to 1M). What DOES break is **flat factored identity**: per-slot resonator capacity at D=10240 is F=3: 65, F=4: 14 (verified law), so V=1M at F=3 needs 100/slot (over capacity) and F≥4 is hopeless; single-token factored readout at 1M would need D≥24k (F=3) or D≥121k (F=4). Chained F=2 hops (H-B4) remain the escape hatch if factored identities are ever wanted. The real large-vocab pressure is the flat codebook's memory + O(V·D) compute — i.e., H-C3's problem, not binding-algebra capacity. `validation/exp_c7_capacity.py`.

## 6. Group D — Backbone architecture hypotheses

This group comes from a single "trillion-parameter architecture blueprint" document the user supplied "to validate and see how it fits." It bundles dynamic tokenization (already covered in Group C), a BDH+TTT backbone, a GCE controller (already the central bet, H0), and AIMC hardware (Group E) into one end-to-end pitch, plus a multiplicative energy-savings calculation. It should not be adopted as a package — each piece is at a different maturity level, and the blueprint itself is a synthesis document, not an implementation.

**H-D1 — BDH's Q=K constrained attention-free recurrence is a candidate backbone for CubbyLLM, one option among others including cubby-lm's MinGRU approach.** Status: PLAUSIBLE — BDH and its `bdh-cl` continual-learning extension are real published architecture work, but the efficiency numbers attached to them (35x faster training, 10x lower inference) come from CIFAR-10/Sudoku-scale experiments, not LLM-scale text modeling. Since CubbyLLM's backbone is being chosen fresh rather than inherited, this is a genuine head-to-head decision, not a replace-in-place question. **Validate** at small scale on a real token-modeling task before assuming these numbers transfer — image/puzzle-benchmark speedups are not evidence about a multi-billion-parameter text model.

**Validation result (2026-07-23 campaign): VIABILITY checked, real decision still deferred.** Matched-size char-LM bake-off (`validation/exp_d1_backbone.py`, d=128/L=4/2500 steps, real valid.txt, cubby-lm's ACTUAL MinGRULayer imported): an attention-free Q=K recurrence learns text competitively (1.584 bpc, far ahead of small softmax attention's 2.470) at lower per-step latency — but **MinGRU is the best learner here** (1.454 bpc, +0.13 over the Q=K mixer).

**RESOLVED (2026-07-23): the in-architecture bake-off picked MinGRU.** `validation/exp_d1b_backbone_bakeoff.py` plugged four candidates into the *real* assembled `CubbyModel` (frozen router → hybrid embedding → backbone → hardened memory → learnable head) on the real subword-TinyStories setup, matched budget, every non-backbone component built from the same per-component seed so the backbone was the only variable. Held-out perplexity / bpc: **gru 34.0 / 1.300, mingru 34.8 / 1.308, bdh(Q=K) 49.1 / 1.435, attn 48.0 / 1.427.** Two clean clusters: gated recurrence (GRU, MinGRU) beats the attention-free Q=K recurrence and softmax attention by ~10% bpc at this scale. GRU vs MinGRU is within single-run noise, but MinGRU matches GRU's quality at **25% fewer backbone params**, with the log-domain parallel scan (throughput at scale, where GRU's kernel is sequential) and continuity with cubby-lm. **User decision: MinGRU is the package default backbone** (`cubbyllm/model/backbone/mingru.py`, `MinGRUBackbone` — a RMSNorm + MinGRU-recurrence + SwiGLU trunk; the interface-only `base.py` keeps alternates pluggable). The 35×/10× BDH efficiency claims remain untested (need scale + a faithful BDH impl); at this scale BDH-Q=K is a viable-but-not-winning contender.

**H-D4 — the H-D1 bake-off chose the backbone on bpc, which is blind to content-based retrieval; a windowed-attention hybrid beats pure MinGRU on long-context recall, at bounded state.** Status: **scale-VERIFIED (2026-08-04) — decisively.** *(Renumbered from a duplicate H-D3; the energy-claim H-D3 below predates this entry.)* The H-D1 bake-off scored on held-out **bpc** — a next-token-prediction metric. Attention's mechanistic edge is *content-based lookup* ("where did this token appear before, and what followed it"), the induction-head circuit, which barely shows up in average perplexity and is exactly what a long-document/needle capability needs. So H-D1 resolved the backbone on the one axis that cannot see the thing at issue. The dense-induction probe (`validation/exp_d3_induction.py`, canonical repeated-sequence task, per-position loss on the second half, d=128/L=6, multi-seed) measures it directly. Result, sweeping distance across the window (`window=96`): at **T=64 (within window)** pure MinGRU **0%**, full-attention hybrid **100%**, windowed hybrid **100%** — bounded state; at **T=256 (beyond window)** MinGRU **0%**, windowed hybrid **0%** (collapses to MinGRU, as it must — a 96-token window cannot reach 256 back), full-attention hybrid still **100%** (unbounded). So the windowed arm buys distance-robust recall out to ~window (×depth for stacked layers) at *fixed, context-independent* state, and no further; full attention solves at any distance but only by paying a KV cache that grows with context. The mechanism is controlled, not inferred (verified: within-window 100% by step 100; beyond-window `W=16,T=32` stuck at chance). This is cubby-lm's own production shape (attention every 3rd layer, 8 of 22, `trunk_torch/blocks.py`), which CubbyLLM had dropped without a decision. **Why windowed, not full:** full attention keeps a KV cache that grows with context, breaking the O(1)-decode guarantee (`tests/model/test_mingru_decode.py::test_state_size_is_independent_of_context_length`) that the inference-cost thesis rests on; a sliding window keeps per-attention-layer state at O(window) = constant. **Built:** `cubbyllm/model/backbone/hybrid.py::HybridBackbone` (MinGRU + windowed attention every Nth, **RoPE** on the attention so it is position-aware — the package has no other positional signal and MinGRU-implicit position would leave layer-0 attention blind; RoPE also extrapolates train-S to the 4096 needle length; bounded-KV `step()` that reproduces `forward()` even across window slides), `__wiring__ = STANDALONE` (pluggable alternate, **not** the default), drops into `CubbyModel` with no assembly change; `tests/model/backbone/test_hybrid.py` (8) pins decode-equivalence, bounded state, window reach + the ~depth×window compounding of stacked windows, and RoPE position-awareness. Wired through `train_colab.py` (`CB_BACKBONE=hybrid`, meta-recorded) and `exp_needle_recall`/`exp_decode_throughput` (reconstruct backbone from meta) so the A/B is a single flag. **Kill criterion / open:** (1) toy-scale only — re-run at the 413M shape on real **needle recall across lengths**, pure-MinGRU vs windowed-hybrid, before making the hybrid the default; (2) the honest limit for the 1M-context pitch — *no* bounded-state model does arbitrary-distance recall; windowed attention extends distance-robust recall to ~depth×window tokens at fixed state, and beyond that recall falls back to what the recurrent state retains. `validation/exp_d3_induction.py`, `validation/logs/exp_d3_*`.

**Scale result (2026-08-04): DECISIVE — kill-criterion (1) retired.** Two matched runs, identical except `CB_BACKBONE` — pure MinGRU vs windowed-hybrid (MinGRU + windowed attention every 3rd of 8 layers, `window=512`, RoPE), d=512 / L=8 / ~0.98B tokens each — scored on `exp_needle_recall` (PMI, shuffled + untrained controls, argmax-spread check) across lengths **256 / 512 / 1024 / 4096**. Floor: MinGRU's shuffled control ~15%, untrained ~33% (a PMI base-rate residual), chance 12.5%. **Pure MinGRU (trained): ~28–32% at every length** — barely above its own shuffled floor, flat, weak. **Windowed hybrid (trained): ~98% at 256, ~100% at 512** (every depth except the window-edge depth 0.0 = 41.7%), and at **1024 the depth pattern IS the window, drawn to a single step:** `16.7 / 16.7 / 8.3 / 91.7 / 100` — chance while the needle sits beyond the 512 window (depths 0.0–0.5), near-perfect once it is inside it (depths 0.75–1.0), the transition landing exactly at the window boundary. Recall is a pure function of one variable — **needle-to-query distance vs window**: inside → ~100%, outside → chance. That fingerprint rules out memorisation or artifact; it is the sliding-window mechanism itself, at scale. So a windowed-attention hybrid gives near-perfect long-context recall within its window at bounded, context-independent state, and pure recurrence does not (**98% vs 32%** at 256). The honest bound is in the same data: beyond the window the hybrid falls to the floor like MinGRU — windowed attention buys perfect recall to ~window (×depth for stacked layers), no further; recall *past* the window is the memory layer's job (rung 0.0.5, still unbuilt). **Decision: the backbone is the hybrid** — H-D1's "RESOLVED: MinGRU" is superseded; it was resolved on the one metric (bpc) that cannot see retrieval. `validation/logs/needle_mingru.log`, `validation/logs/needle_hybrid.log`.

**H-D2 — In-place Test-Time Training eliminates the KV-cache but is a compute-for-memory trade, not a free win.** The blueprint proposes repurposing FFN projection layers as dynamically-updated fast weights during inference, updated via local next-token-prediction gradients, to handle long context (128k tokens) without KV-cache memory-bandwidth cost. Status: SPECULATIVE as a net win — TTT's per-token update is itself a gradient step, so inference compute per token goes up even as cache memory goes down. **Validate** by measuring wall-clock/FLOPs per generated token with TTT-in-the-loop versus standard KV-cache attention at matched context length — the blueprint only argues the memory side, not the compute side, of this trade.

**Validation result (2026-07-23 campaign): compute side now measured (d=512, CPU, rank-1/NLMS-style update — the cheap TTT variant).** TTT per-token cost is constant 0.253ms; KV-attention grows 0.545→210.4ms from L=1k→131k; measured crossover **L≈1,024 (≈d)** — so on this shape the compute side *also* favors TTT for essentially all long-context regimes, rather than opposing the memory win (1.0MB vs 536.9MB state at 128k). **H-D3 — HIGH SCRUTINY: the blueprint's ~2,250x (reduced to "~1,900x" after a 15% overhead haircut) total energy-reduction claim should not be treated as a real number.** It's constructed by multiplying four independently-sourced factors: ~90x from eliminating weight-loading via analog in-memory compute, 2.5x from zip2zip-style sequence compaction, 5x from spike-based activation sparsity, 2x from softmax/KV-cache bypass. Status: SPECULATIVE, and specifically flagged here because multiplying independently-sourced efficiency claims from four different papers/contexts is not evidence they compose in one real system — savings mechanisms frequently target overlapping bottlenecks (if weight-loading is already ~90x cheaper via analog compute, the marginal value of also cutting softmax cost is not obviously still a clean independent 2x on top), and none of these four numbers were measured together in a single working pipeline anywhere in the source material. **Validate only by building an integrated small-scale prototype and measuring the composed number directly.** Treat 1,900–2,250x as a theoretical ceiling under best-case independence assumptions, never as a planning number.

## 7. Group E — Hardware and economics (explicitly gated, long-horizon)

**H-E1 — Analog In-Memory Computing could deliver the claimed ~100x energy reduction, but requires silicon that doesn't exist for this project.** The blueprint proposes memristive crossbar arrays computing matrix-vector multiplication via Ohm's/Kirchhoff's law directly in memory, sub-1V reset-only weight updates (claimed 460x lower programming energy than digital backprop), and event-driven LIF spiking cores. ## 9b. Group P — Prospection: branching futures, timescales, keyframe compression (added 2026-08-25)

Origin: a design conversation (2026-08-25) framing a "5th dimension" — the landscape of alternate futures and pasts indexed by the choices made along the 4D trajectory — as a capability target: counterfactual timelines ("what if Alexander the Great was never born?") and goal-directed choice selection by predicted short/medium/long-term outcomes. Operationally the object is path space with a measure over it, and an LM already contains it implicitly (every softmax is a one-step fan of branches); what it lacks is an explicit handle. The five hypotheses below are the parts that are *about this architecture* and cheaply falsifiable now. The parts that are not — a causal graph over history with a stated held-fixed set, multi-γ successor-feature heads, eligibility traces plus episodic write-back for delayed credit, goal vectors with generalized policy improvement, Dyna-style dreaming behind a grounding filter, provenance-tagging of imagined episodes in the store — are a roadmap, not claims, and are deliberately NOT entered here until each has a cheap experiment. Scripts: `validation/prospection/` (its README has the run matrix and the checkpoint env vars); `validation/prospection/test_prospection.py` runs all five quick. Toy-scale numbers are d=32, L=2, CPU — mechanism demonstrations; the checkpoint arms ran the same day on `D:\My Drive\cubbyllm\ab_hybrid.pt` (d=512/L=8, the H-D4 winner) and `hd5_mem2.pt`, and where the two disagree the checkpoint is the one that counts.

**H-P1 — The decode state is a forkable world snapshot: branching from it is exact, O(1) in context length, and isolated.** Source: `HybridBackbone.step` / `MinGRUBackbone.step` carry fixed-size state (the H-D4 bounded-decode guard), and `exp_needle_recall.py` already branches candidates from one prefix state. Validate: k branches from one cloned state vs k independent full passes; state floats vs prefix length; origin/store isolation. Kill: any fp drift, any growth with prefix, any leak. **Validation result (2026-08-25): VERIFIED at toy scale** — max |forked − independent| = 0.00e+00 on mingru, hybrid and hybrid+episodic-memory; state floats 96 / 577 / 1345 constant across prefixes 8/32/64; no origin mutation, no store leak; 96 vs 240 `step()`s for 4 branches (`validation/logs/exp_p1_fork_equivalence.log`). **Checkpoint arm (same day): VERIFIED at scale** on `ab_hybrid.pt` (d=512/L=8, the H-D4 winner) and `hd5_mem2.pt` (+ episodic memory every 2nd layer): exact at 0.00e+00 on both; state bounded past the window at 1,575,427 floats (≈6.3 MB — 1,572,864 of them the three attention KV caches, 2,560 the five recurrent layers) and 2,755,075 with the memory FIFOs; store isolation holds at scale (`validation/logs/exp_p1_fork_equivalence_ab_hybrid.log`, `_hd5_mem2.log`). **Honest cost accounting:** the hybrid's fork/keyframe cost is the attention window, not the recurrence — a snapshot re-enterable without the preceding 512 tokens is ~6 MB, not ~10 KB; with tokens stored, a recurrent-only keyframe at t−window plus a 512-step recompute is exact and small. This is the structural argument for building counterfactual machinery on this backbone rather than on a KV cache that grows with context, and it is the primitive H-P4/H-P5 rely on.

**H-P2 — Choice points are sparse and the model's own next-token entropy localizes them, so "open branches only at high-entropy steps" is a budget rule with a real signal behind it (vicarious trial and error happens only at decision points).** Source: the design conversation; Redish (2016) for the biological shape. Validate: on the branch grammar (exactly one free choice per 8-token segment, everything else deterministic) AUROC of entropy vs the labeled choice positions on the parallel and the decode path; flagged fraction vs the true 1/8. Kill: AUROC well under 0.9 or the fraction far off. **Validation result (2026-08-25): VERIFIED at toy scale** — loss 0.198 nats/token vs the grammar floor 0.173; entropy 1.375 (≈ ln 4) at choice points vs 0.002 elsewhere; AUROC 1.000 on both paths; flagged fraction 0.125 (`validation/logs/exp_p2_choice_points.log`). **Checkpoint arm (same day): the toy result does NOT transfer as-is.** On `ab_hybrid.pt` over 4,095 positions of real Wikipedia text (80 articles across the 20 domain files next to the checkpoints, `grillcheese_bbpe128k.json`): entropy median 4.32 nats, p90 6.14; fraction above 1 / 2 / 3 nats = **0.914 / 0.830 / 0.701** (`validation/logs/exp_p2_choice_points_ab_hybrid.log`). At this scale choice points are not sparse — an absolute threshold would open branches at 70–90% of steps. Status of the *budget rule*: **PLAUSIBLE, needs reformulation** — a relative criterion (entropy above the model's running median, or the top decile within a window) or a stronger model; the detector claim (entropy localizes the choices that exist) stands, the sparsity claim is a property of the model's confidence, not of text.

**H-P3 — The MinGRU retention gate is uniformly short-memory at init, cannot represent time constants above ~1000 steps, and only lengthens as far as the data forces it; a chrono-style init spreads the spectrum over decades without touching the scan or the decode path.** Source: `mingru.py` (`a = 0.001 + 0.998·σ(proj_d x)`, bias init 1.0); Tallec & Ollivier 2018 (chrono init); Murray et al. 2014 (cortical hierarchy of intrinsic timescales). Validate: per-unit τ = −1/ln a from the geometric-mean retention over real inputs at init / after toy training / after chrono init; pin the formula against `_MinGRUMixer.step`; delayed copy default-vs-chrono at lags 8/32/128. Kill: any of the three substrate facts wrong. **Validation result (2026-08-25): VERIFIED at toy scale** — init τ p50 ≈ 2.8 steps for every unit; **τ ceiling 999.5 steps** (a ≤ 0.999 by construction); toy training moved no unit past τ ≈ 4 (its longest dependency is 3 steps — gates lengthen only as far as the data demands); chrono init τ p10/p50/p90 ≈ 2.4 / 15 / 260 with 22% of units slower than 100 steps; delayed copy (300 steps, informational): default init sits at chance beyond lag 8 (2.71 vs ln 16 = 2.77) while chrono reaches 2.52 at lag 32 and 2.60 at lag 128 (`validation/logs/exp_p3_gate_spectrum.log`). **Checkpoint arm (same day) — the load-bearing finding of the group:** on `ab_hybrid.pt` over 2,048 real tokens the five recurrent layers have median τ = 0.5 / 0.7 / 1.1 / 1.5 / 1.8 steps (layers 1/2/4/5/7) — **shorter than init (2.8)**; 0.5% of recurrent units have τ ≥ 8, none ≥ 100, slowest single unit 111 against a cap of 999; conditional latching (instantaneous τ ≥ 100) does not hide long memory either — 1.2% of units latch on ≥10% of steps, the p90 unit on 0.4% (`validation/logs/exp_p3_gate_spectrum_ab_hybrid.log`). **After ~1B tokens the MinGRU layers of the hybrid are 1–2-step mixers; every long-range dependency lives in the three windowed-attention layers.** That is consistent with H-D4 (pure MinGRU ~32% recall vs ~98% for the hybrid inside its window) and it reframes the whole timescales thread: there is no slow subspace in the trained substrate to hang a multi-timescale scheme on — long time constants have to be *made* (chrono init, an explicit long-horizon objective, or an LRU-style rotation-block recurrence), or the timescale machinery lives in attention and the episodic store, where the H-D5 memory rung already is. **Decision pending, not made:** whether the 2B run uses chrono init on its recurrent layers. It is free and decode-neutral, but the long-lag gain is small at d=32 and unmeasured at scale — one pilot arm, not a default, and the checkpoint spectrum above is the arm's baseline. The ceiling is a constraint to carry into any "learn across timescales" design: anything slower than ~1000 steps has to live in the episodic store or the attention window, not in a gate.

**H-P4 — Keyframe compression of the state trajectory should be recompute-from-keyframe (exact, cheap by H-P1), not interpolation; interpolation earns its place only on slow units, by the sampling theorem.** Source: the AURA note `H:\AURA_MIND\papers\temporal_memory_interpolation.md` (memory compression as keyframes + regenerated in-betweens via Hilbert / Hamiltonian / Fourier interpolation); Delétang et al. 2023 for the wider prediction-is-compression principle. Validate: linear-interpolation error vs hold-last per gap; per-unit error vs τ; recompute error; bytes/step; numerical pins on the note's operators. Kill: interpolation not under hold-last at gap 4; recompute not exact. **Validation result (2026-08-25): VERIFIED at toy scale, and the note's operators are FALSIFIED as written** — with two keyframes and no time axis, the Hilbert and Fourier strategies equal plain linear interpolation to 4e-16 (Re and F are linear maps), and the rank-one Hamiltonian flow conserves the analytic-signal norm (drift 4e-10) and misses keyframe 1 by 0.715 relative — it rotates one component's phase, it does not travel; on the toy (τ ≈ 3) linear interpolation rel-RMS 0.59 / 0.83 / 1.16 at gaps 2 / 4 / 8 vs hold-last 0.80 / 1.03 / 1.26 — barely better than doing nothing, worse than the unit mean from gap 8; Spearman(log τ, error) = −0.38, so slow units do interpolate better and the multi-resolution rule has signal; recompute exact at 0.0e+00; 256 B/step of states vs 32.5 B/step for keyframes + tokens at gap 8 (`validation/logs/exp_p4_keyframe_interp.log`). **Checkpoint arm (same day): VERIFIED at scale, same verdict, stronger** — on `ab_hybrid.pt` over a 1,024-token real trajectory (5 recurrent layers × 512): linear interpolation rel-RMS 0.74 / 0.87 / 1.00 / 1.10 / 1.17 at gaps 2 / 4 / 8 / 16 / 32 vs hold-last 0.92 / 1.10 / 1.21 / 1.30 / 1.34 — worse than the unit mean from gap 8; Spearman(log τ, per-unit error) = **−0.88**; recompute exact at 0.0e+00; recurrent state 10,240 B/step vs 1,282 B/step for keyframes + tokens at gap 8, with the attention KV cache on top per H-P1 (`validation/logs/exp_p4_keyframe_interp_ab_hybrid.log`). **H-P5 — Counterfactual re-entry works mechanically on a world the model fully knows: snapshot at a choice point, substitute the choice, re-run, and the continuation switches to the ground-truth alternative while overdetermined outcomes stay put.** Source: Pearl's ladder (abduction → intervention → prediction) with the recurrent state as the abduced latent; the design conversation's fragile-vs-overdetermined distinction. BinaryOps/HolographicOps remain reference implementations, not the standard. **Two grilly hazards found while surveying it for reusable VSA work (2026-08-02).**

(a) **`blockcode_bind` exists twice with different semantics, and one silently corrupts bundles.** `grilly.experimental.vsa.block_ops.BlockCodeOps.bind` (what `cubbyllm.ops.BlockCodeVSA` actually calls) is true per-block circular convolution. `grilly.backend._bridge.blockcode_bind` — both the GPU shader `shaders/blockcode-bind.glsl` and its numpy fallback — is a one-hot **argmax shift**: it scans `if (a[i] > 0.5) hot_a = i`, so on a continuous block code (every entry < 0.5, since each block sums to 1 across l slots) both indices stay 0 and it returns the **identity element without raising**. CubbyLLM is safe only because its ops seam never dispatches to `_bridge` — see the TODO item, which now says *do not* wire that dispatch. grilly's own `tests/test_blockcode.py` cannot catch this because every test uses strictly one-hot inputs; there is no test anywhere in grilly that unbinds from a superposition. Ours now has three: `tests/ops/test_vsa.py`.

(b) **`blockCodeCodebook` caps at n <= l — 128 codes at l=128.** IBM's successive-binding construction walks the cyclic group Z_l per block with the same shift each step, so it wraps after exactly l entries; the C++ raises `n must be <= l`, and the Python twin *silently* degrades to random sampling "(may have collisions for large n)". Irrelevant for role/filler duty (n=16), but it means the decided k=80 x l=128 shape cannot supply a large concept codebook by that construction. Independent random one-hot per block gives ~l^k distinct codes with birthday-bounded collisions, at the cost of algebraic closure — budget that design choice before the VM needs a vocabulary-scale codebook.
