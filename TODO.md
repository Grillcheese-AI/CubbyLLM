# CubbyLLM — TODO

Working checklist for what's left after the 2026-07-23 validation campaign and first implementation pass. All four structural decisions are made (binding algebra, vocab shape, backbone, memory approach — see `CLAUDE.md`) and a first-pass `cubbyllm/` package already trains end-to-end on a toy corpus. Everything below is what's left before that becomes a real model, plus a few smaller follow-ups the campaign surfaced. Check items off as they're done. If a new one comes up mid-work, add it here the same way a hypothesis gets added to `CUBBYLLM_HYPOTHESES.md` — with enough context that a future session doesn't have to re-derive why it matters.

## Architecture work still open

- [ ] **Build real VSA unbind on the VM/reasoning side.** The validation campaign found the placeholder `UNBIND_ROLE` lives in cubemind's `reasoning/vm.py:602-606`, not cubby-lm's LM head — the LM head itself turned out to be clean, well-engineered code with no unbind mechanism at all. No real unbind implementation exists on the VM side yet. Natural candidate: the now-decided `BlockCodeOps` algebra.
- [ ] **Define the Cubby↔CubeMind bridges concretely (H-F2).** H0's validated mechanism implies the bridges need to carry a context/task embedding in both directions plus generated-parameter/specialist handles. Neither current bridge (`NoveltyToWorldBridge`, the CubeLang subprocess bridge) carries either. This was explicitly deferred until the backbone/vocab/binding decisions landed — they have, so this is unblocked.
- [ ] **Re-verify `CUBEMIND_CLEANUP_PLAN.md`'s status table before starting either item above.** Its own numbers already drifted from cubemind's own refactor plan once in a single day — confirm `sandbox/`, `_archive/`, MoQE, and the `core`/`functional` duplication haven't shifted again, and specifically that `ops/block_codes.py` and `reasoning/vm.py` (the two files the unbind and bridge work actually touch) haven't moved or changed shape.
- [ ] **Scale H0 past toy scale.** Everything validated so far (the hardening countermeasure, the offline-pretrained router, both forgetting benchmarks) used small D, a handful of tasks, CPU only. Two specific unknowns: how the hardening's compute cost grows with the number of protected contexts, and whether the mechanism stays correctly scoped to the memory pathway once it's inside a real (not toy) network.
- [x] **H-B6 CLOSED NEGATIVE (2026-08-02) — set `CB_BIND_W=0` for the DDP run.** The binding aux loss is Goodhart-able and the trunk took the degenerate solution: it rewards cosine-to-own-filler with no penalty on cosine-to-other-fillers, so collapsing a sequence's hidden states onto one direction scores ~0.86. Measured on the trained ckpt at n=16: cos 0.840 but **retrieval 11.5%** (chance 6.25%) against an **untrained control at 97.5%** — training made the trunk far worse at the one thing binding is for. Reproduced synthetically (filler-filler cosine 0.006→0.974 as cos rises). A contrastive/InfoNCE reformulation prevents the collapse but buys nothing over random init, because **an untrained trunk is already a near-optimal VSA substrate** — high-dimensional random vectors are quasi-orthogonal by construction. Do not re-add a binding objective without a metric that measures discrimination, and do not expect one to help. See H-B6 in `CUBBYLLM_HYPOTHESES.md` and `validation/logs/exp_b6_blockcode_transfer.log`.
- [ ] **Superseded — was: close out H-B6 (is the binding aux loss truly free?).** The 2026-07-30 live 2B run showed the MAP binding loss falling to a ~0.20 plateau while bpc kept dropping through the full-LR onset out to step 3000 — the *mechanism* (trunk becomes VSA-bindable via a zero-parameter loss) is VERIFIED, but "free" is only PLAUSIBLE. Still to close: (a) capture the clean A/B — the no-binding `ckpt_1` bpc at matched steps, which wasn't logged numerically; (b) confirm bpc never diverges from a no-binding baseline at full-run (~40B-token) scale; (c) **verify MAP-scheme bindability actually transfers to the production `BlockCodeOps` algebra** — the aux loss uses MAP only because it's differentiable; the VM channel is a different VSA family, and transfer is untested; (d) show a bindable trunk `h` makes VM-side unbind (H-B3) work downstream (aux-probe capacity ≠ usable relational readout). Also **tee the live/DDP training log to `validation/logs/` in full** per the persist-experiment-logs rule — current evidence (`validation/logs/binding_aux_loss_live_2b_2026-07-30.log`) is hand-copied milestone lines, not a full tee.

## Smaller follow-ups

- [ ] **`ops/vsa.py` advertises a Vulkan tier it never calls.** `_detect_backend()` reports `grilly_bridge` when `_bridge.blockcode_bind` exists, but `_load_grilly_ops()` loads grilly's **Python** `BlockCodeOps` and every method dispatches to `self._ops` — the C++/Vulkan bridge is detected and never used. No correctness impact (all three tiers compute the same per-block FFT circular convolution, verified 2026-08-02 against grilly's source), but `backend()` misreports what actually ran, which matters for any perf claim and is this repo's own "built but never wired in" pattern living inside the ops seam. Either dispatch to the bridge or rename the label.
- [ ] **Move cubemind's I-RAVEN block shape to the decided k=80 x l=128 (d=10240).** It runs at k=16 x l=128 = d=2048, 5x under the standardized H-B5 algebra, and multi-entity grid configs plateau at 67-77% against 96-100% for single-entity — a capacity ceiling at 9 bundled objects. Prefer the decided shape over the note's proposed 32x256=8192: it keeps l=128 so codebooks and shaders stay compatible, and preserves the one-algebra property. Expect ~2.2x SNR (crosstalk ~1/sqrt(D)), not the "exponential" gain the note claims. Pair it with SequentialHyperGraph-style cleanup between bundling levels. See H-B4.

- [ ] **Re-check H-C1 (hyper-encoder embedding quality) at real scale.** The toy-scale result used a pure surface-form generator and lost about 0.5 nats versus a static embedding table. A context-conditioned generator, or zip2zip-style composition over the now-decided static core, could flip this — untested at the scale that matters.
- [ ] **Resolve the H-B5 generalization question.** grilly's SVC role-filler binding scheme was built for subject/verb/context triples. Whether it generalizes cleanly to CubbyLLM's actual token/concept binding needs is still open.
- [ ] **Sign off on `PACKAGE_LAYOUT.md`.** Status is currently PROPOSAL — the implementation pass has followed it in practice, but nobody's explicitly confirmed it as final.
